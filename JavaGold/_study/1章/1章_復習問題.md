## 2. ジェネリクス

### 復習2-1

```java
1  import java.util.ArrayList;
2  import java.util.List;
3
4  public class Main {
5      static void addNumber(List<? extends Number> list) {
6          list.add(Integer.valueOf(1));
7      }
8      public static void main(String[] args) {
9          List<Integer> list = new ArrayList<>();
10         addNumber(list);
11     }
12 }
```

6行目を実行するとどうなるか。

A. `list`に`1`が追加される

B. 6行目で`UnsupportedOperationException`がスローされる

C. 6行目でコンパイルエラーになる

D. 6行目で`ClassCastException`がスローされる

答え A(アドナンバーのジェネリクスがリストよりも下のサブクラスだから、これはアドナンバーが使用できる。)
正解 C
解説: `List<? extends Number>`は「中身が`Number`のどのサブタイプか分からない、読み取り専用」の型。`Integer`が`Number`のサブクラスであることは追加を許可する理由にはならず、コンパイラは安全側に倒して`add()`を一切禁止する(`null`だけ例外)。これがPECS原則の"Extends=取り出し専用"。

### 復習2-2

```java
1  import java.util.Arrays;
2  import java.util.List;
3
4  public class Main {
5      static void printAll(List<?> list) {
6          list.add("x");
7      }
8      public static void main(String[] args) {
9          printAll(Arrays.asList("a", "b"));
10     }
11 }
```

6行目を実行するとどうなるか。

A. `list`に`"x"`が追加される

B. 6行目で`UnsupportedOperationException`がスローされる

C. 6行目でコンパイルエラーになる

D. 9行目で`ClassCastException`がスローされる

答え　B
正解 C
解説: `List<?>`は「型が何であれ、既存の要素以外は一切追加できない」ワイルドカード型。`?`は「何かの具体的な型」を表すが、その正体をコンパイラは特定できないため、どんな型の値(`"x"`含む)も`add()`できない(`null`のみ例外)。`? extends Number`と同じ理屈で、未知の型に対しては書き込み不可というのが徹底されている。

## 3・4. コレクションフレームワーク

### 復習3-1

```java
1  import java.util.ArrayDeque;
2  import java.util.NoSuchElementException;
3  import java.util.Queue;
4
5  public class Main {
6      public static void main(String[] args) {
7          Queue<String> queue = new ArrayDeque<>();
8          System.out.println(queue.poll());
9          queue.remove();
10     }
11 }
```

8行目・9行目を実行するとどうなるか。

A. `null` → 9行目で`NoSuchElementException`がスローされる

B. `null` → 9行目は何も起きず正常終了する

C. 8行目で`NoSuchElementException`がスローされる

D. 8行目でコンパイルエラーになる

答え A
正解 A
解説: `poll()`/`peek()`は「空でも例外を投げず`null`を返す」安全系メソッド。一方`remove()`/`element()`は「空なら`NoSuchElementException`をスローする」厳格系メソッド。同じ「取り出す」でも、Queueには失敗を`null`で表す系統と例外で表す系統の2系統があり、`poll()`後にキューが空のまま`remove()`を呼んだので例外になる。

### 復習3-2

```java
1  import java.util.HashMap;
2  import java.util.Map;
3
4  public class Main {
5      public static void main(String[] args) {
6          Map<String, String> map = new HashMap<>();
7          map.put(null, "A");
8          System.out.println(map);
9          Map.of(null, "A");
10     }
11 }
```

7行目・9行目を実行するとどうなるか。

A. 7行目で`NullPointerException`がスローされる

B. 7行目は成功する → 9行目で`NullPointerException`がスローされる

C. 7行目・9行目とも成功する

D. 7行目でコンパイルエラーになる

答え　B
正解 B
解説: `HashMap`は`null`キーを1個だけ許容する(内部でハッシュ値0の特別扱いバケットとして処理)ため、`put(null, "A")`は普通に成功する。一方`Map.of()`は`null`を一切許さない設計なので、キーであれ値であれ`null`を渡すと生成時点で`NullPointerException`になる。同じ「Mapを作る」でも、可変な実装クラスと`of()`の不変コレクションで`null`への態度が正反対という対比がポイント。

### 復習3-3

```java
1  import java.util.HashSet;
2  import java.util.Set;
3
4  public class Main {
5      public static void main(String[] args) {
6          Set<Long> set = new HashSet<>();
7          set.add(1L);
8          boolean removed = set.remove(1);
9          System.out.println("removed=" + removed + " set=" + set);
10     }
11 }
```

8行目・9行目を実行するとどうなるか。

A. `removed=true set=[]`

B. `removed=false set=[1]`

C. 8行目でコンパイルエラーになる

D. 8行目で`ClassCastException`がスローされる

答え　B!
正解 B
解説: `Set<Long>`に`remove(1)`(int)を渡すと、まず`int`が`Integer`にオートボクシングされる。しかし`Set.remove(Object o)`の中身の判定は`equals()`で行われ、`Integer`と`Long`は値が同じ`1`でも**クラスが違うため`equals()`はfalseを返す**(`Integer.equals()`の実装は「相手が`Integer`かどうか」も見ている)。よって削除は起きず`removed=false`、`set`の中身も変わらない。例外にもならず、コンパイルも通る(`remove(Object)`は何でも受け取れる)、という「静かな失敗」が本質。

### 復習3-4

```java
1  import java.util.ArrayList;
2  import java.util.List;
3
4  public class Main {
5      public static void main(String[] args) {
6          List<String> list = new ArrayList<>();
7          list.add("A");
8          list.add("B");
9          list.add("C");
10         for (String s : list) {
11             if (s.equals("B")) {
12                 list.remove(s);
13             }
14         }
15         System.out.println(list);
16     }
17 }
```

12行目を実行するとどうなるか。

A. `[A, C]`と出力される(例外は起きない)

B. `[A, B, C]` → 10行目のループで`ConcurrentModificationException`がスローされる

C. `[A, C]` → 15行目で`ConcurrentModificationException`がスローされる

D. 12行目でコンパイルエラーになる

答え　A!
正解 A
解説: 拡張for文はリストの要素数3個に対して「インデックス0,1,2まで見る」という単純な仕組みではなく、内部的に`Iterator`の`hasNext()`/`next()`を呼んでいる。`"B"`(インデックス1)を`list.remove(s)`で直接削除すると、リストのサイズは3→2に減り、内部カーソルは2になる。次の`hasNext()`が「カーソル(2) == サイズ(2)」を見て「もう次はない」と判定してループを正常終了してしまうため、`ConcurrentModificationException`を検出する前にループが終わり、例外なく`[A, C]`が出力される。3要素中の**ちょうど真ん中(後ろから2番目)を消したときだけ**この「例外が起きない」偶然が起きる、という際どいケース(4要素以上で真ん中以外を消すと普通に例外が起きる)。

## 5. コレクションのソート

### 復習5-1

```java
1  import java.util.Set;
2  import java.util.TreeSet;
3
4  class Item {
5      String name;
6      Item(String name) { this.name = name; }
7      public String toString() { return name; }
8  }
9
10 public class Main {
11     public static void main(String[] args) {
12         Set<Item> set = new TreeSet<>();
13         set.add(new Item("A"));
14         System.out.println(set);
15     }
16 }
```

13行目を実行するとどうなるか。

A. `[A]`と出力される

B. 13行目で`ClassCastException`がスローされる

C. 12行目でコンパイルエラーになる(`Item`が`Comparable`を実装していないため)

D. 13行目で`NullPointerException`がスローされる  
答え C!
正解 B
解説: `TreeSet<E>`のクラス宣言自体に`<E extends Comparable<E>>`のような境界が付いていない(`public class TreeSet<E> ...`のみ)ため、コンパイラはそもそも`Item`が`Comparable`かどうかを確認する材料を持たず、常にコンパイルが通る。対して`Collections.sort()`は`<T extends Comparable<? super T>>`という境界を明示的に宣言しているため、`Item`のままraw型を使わずに渡すと本来はコンパイルエラーになる(この対比が重要)。`TreeSet`は境界チェックを実行時の`add()`に委ねており、呼ばれた瞬間`TreeMap`内部で`(Comparable) e`へのキャストが実行される。`Item`は`Comparable`を実装していないため**1個目の要素を追加した時点で`ClassCastException`**になる(2個目の追加を待たずに、最初のadd()で即座に落ちる)。

### 復習5-2

```java
1  import java.util.ArrayList;
2  import java.util.Collections;
3  import java.util.Comparator;
4  import java.util.List;
5
6  public class Main {
7      public static void main(String[] args) {
8          List<Integer> list = new ArrayList<>();
9          Collections.addAll(list, 3, 1, 2);
10         Collections.sort(list, Comparator.reverseOrder());
11         System.out.println("desc: " + list);
12         Collections.sort(list);
13         System.out.println("after sort(): " + list);
14     }
15 }
```

12行目を実行した後の`list`はどうなるか。

A. `[3, 2, 1]`のまま変化しない(直前の`reverseOrder()`が記憶されている)

B. `[1, 2, 3]`(自然順序で再ソートされる)

C. 12行目で`IllegalStateException`がスローされる(すでにComparator付きでソート済みのため)

D. 12行目でコンパイルエラーになる(引数無しの`sort()`は一度Comparatorを使うと呼べない)

答えB!
正解 B
解説: `Collections.sort(list, comparator)`は「リストという状態を、その呼び出し時点のルールで並べ替える」という**その場限りの操作**であり、「以降ずっとこのComparatorで固定する」というモードに切り替わるわけではない。`list`自体は`Comparator.reverseOrder()`を覚えているわけではなく、単に一時的にその順番に並んだ普通の`List<Integer>`。その後`Collections.sort(list)`(Comparatorなし)を呼べば、要素が実装している自然順序(`Comparable`)で普通に再ソートされ、`[1, 2, 3]`になる。

## 6. コレクション用の便利なメソッド

### 復習6-1

```java
1  import java.util.ArrayList;
2  import java.util.Collections;
3  import java.util.List;
4
5  public class Main {
6      public static void main(String[] args) {
7          List<String> base = new ArrayList<>();
8          base.add("A");
9          base.add("B");
10         List<String> view = Collections.unmodifiableList(base);
11         base.add("C");
12         System.out.println(view);
13         view.add("D");
14     }
15 }
```

12行目・13行目を実行するとどうなるか。

A. `[A, B]` → 13行目で`UnsupportedOperationException`がスローされる

B. `[A, B, C]` → 13行目で`UnsupportedOperationException`がスローされる

C. `[A, B, C]` → 13行目で`D`が追加され`[A, B, C, D]`になる

D. 10行目でコンパイルエラーになる

答えB!
正解 B
解説: `Collections.unmodifiableList(base)`が返す`view`は、`base`のコピーではなく**元のリストへの生きたビュー(窓)**。`base`に後から`"C"`を追加すれば、その変更は`view`越しにも見える(`view`が独自にデータを持っているわけではないため)。ただし`view`自身から`add()`/`remove()`/`set()`を呼ぶことだけは禁止されており、`UnsupportedOperationException`になる。「変更禁止なのは`view`という窓口からの操作だけで、元の`base`はいつも通り自由に変更できる」という点が本質。

### 復習6-2

```java
1  import java.util.ArrayList;
2  import java.util.List;
3
4  public class Main {
5      public static void main(String[] args) {
6          List<String> base = new ArrayList<>();
7          base.add("A");
8          base.add("B");
9          List<String> copy = List.copyOf(base);
10         base.add("C");
11         System.out.println("copy: " + copy);
12         copy.add("D");
13     }
14 }
```

11行目・12行目を実行するとどうなるか。

A. `copy: [A, B]` → 12行目で`UnsupportedOperationException`がスローされる

B. `copy: [A, B, C]` → 12行目で`UnsupportedOperationException`がスローされる

C. `copy: [A, B]` → 12行目で`D`が追加され`[A, B, D]`になる

D. 9行目でコンパイルエラーになる



答えB!
正解 A
解説: `List.copyOf(base)`は呼ばれた**その瞬間の中身をスナップショット(コピー)**して、全く別の不変な`List`を新しく作る。`Collections.unmodifiableList()`(復習6-1)のような「元のリストへの生きたビュー」ではないので、後から`base`に`"C"`を追加しても`copy`には一切反映されず、`copy`は`[A, B]`のまま。さらに`copy`自体`List.of()`同様の完全な不変コレクションなので、`add()`は`UnsupportedOperationException`になる。「ビューか、スナップショットか」の違いが復習6-1との対比ポイント。
