## 問題1

`char c = 3 + 'a';`は、キャストなしでコンパイルできますか？理由も答えてください。

<details><summary>解答</summary>

**できます。**`3`も`'a'`も両方コンパイル時定数なので、`3 + 'a'`はコンパイルの時点で`100`という値に確定します。`byte`・`short`と同じく、`char`も「右辺が定数式で、値がその型の範囲に収まっていれば、キャストなしで代入できる」というルールが適用されるためです。

</details>

## 問題2

`int i = 97; char c = i;`（`i`はただの変数）は、キャストなしでコンパイルできますか？問題1との違いも答えてください。

<details><summary>解答</summary>

**できません。**「不適合な型: 精度が失われる可能性があるintからcharへの変換」というコンパイルエラーになります。問題1の`3 + 'a'`はコンパイル時に値が確定する**定数式**でしたが、今回の`i`はただの**変数**です。変数の場合、コンパイラは実行時にどんな値が入るか分からないため、値が実際にchar の範囲に収まるかどうかに関係なく、キャストが必須になります。

</details>

## 問題3

`char`から`int`への変換と、`int`から`char`への変換、キャストが要らないのはどちらですか？

<details><summary>解答</summary>

**`char`から`int`です。**`char`（0〜65535）は`int`より表せる範囲が狭いので、`int i = someChar;`のように拡大変換（ワイドニング）になり、キャストなしで代入できます。逆に`int`から`char`は縮小変換（ナローイング）なので、変数が相手の場合は必ずキャストが必要です（問題1のように定数式なら例外的にキャスト不要）。

</details>

## 問題4

`javac -d classes bar/Two.java foo/One.java`を実行すると、生成された`.class`ファイルはどこに置かれますか？

<details><summary>解答</summary>

**コマンドを実行した「今いるフォルダ」の中に、`classes`フォルダが作られ、その中にパッケージ名に対応したフォルダが作られます。**（例：`package ex6.bar;`のクラスなら`classes/ex6/bar/Two.class`）。ソースファイルがどこにあるかではなく、**javacを実行した場所（カレントディレクトリ）が基準**になります。

</details>

## 問題5

上の`classes/ex6/bar/Two.class`（`package ex6.bar;`）を実行するには、`java`コマンドをどう書けばいいですか？

<details><summary>解答</summary>

**`java -cp classes ex6.bar.Two`のように書きます。**`-cp`（クラスパス）には、`.class`ファイルたちの置き場所（今回は`classes`フォルダ）を指定します。実行するクラス名は、`Two`だけでなく、**パッケージ名を含めた完全修飾名**（`ex6.bar.Two`）で指定する必要があります。`-cp`を付けなかったり、パッケージ名を省略すると「ClassNotFoundException」でエラーになります。

</details>

## 問題6

`boolean b = new Boolean[1][2];`と`int[][] i = new Integer[1][2];`は、それぞれコンパイルできますか？

<details><summary>解答</summary>

**どちらもできません。**`boolean b = ...`は「配列 vs 非配列（次元違い）」の不一致、`int[][] i = new Integer[1][2];`は「プリミティブ配列 vs ラッパー配列」の型不一致です。プリミティブ配列（`int[]`）とラッパー配列（`Integer[]`）はJVM内部で完全に別の型（`[I` vs `[Ljava.lang.Integer;`）として扱われるため、次元を揃えても型そのものが違えばエラーになります。オートボクシングは「値1個」の変換であって、配列の型変換には適用されません。

</details>

## 問題7

`Number[] n = new Integer[3];`はコンパイルできますか？また逆に`Integer[] i = new Number[3];`はどうですか？

<details><summary>解答</summary>

**`Number[] n = new Integer[3];`はできます**が、**`Integer[] i = new Number[3];`はできません。**`Integer`は`Number`のサブクラスなので、参照型の配列は要素型の継承関係と同じ方向にだけ共変（covariant）します。ただしこれは`int[]`と`Integer[]`のようなプリミティブ/ラッパー配列の間では成立しません（問題6参照）。

</details>

## 問題8

`var d2 = {{2.0}};`（配列の初期化子だけを右辺に書く）はコンパイルできますか？

<details><summary>解答</summary>

**できません。**「配列初期化子には明示的なターゲット型が必要です」というエラーになります。`{{2.0}}`のような初期化子はそれ単体では型を持たない特殊な構文で、左辺に型が明示された変数宣言（`double[][] d2 = {{2.0}};`）でしか使えません。`var`を使うなら、`var d2 = new double[][]{{2.0}};`のように`new 型[]`を含む完結した配列生成式にする必要があります。

</details>

## 問題9

`static`なメソッドと、フィールドは、継承関係があるとき「宣言した型」と「実際のオブジェクトの型」のどちらを基準に呼び出されますか？インスタンスメソッドとの違いも教えてください。

<details><summary>解答</summary>

**どちらも「宣言した型（静的型）」を基準に決まります。**インスタンスメソッドだけが動的束縛（実際のオブジェクトの型で決まる、ポリモーフィズム）の対象で、staticメソッドとフィールドは宣言型で固定されます。例えば`Top t = new Bottom();`として`t.staticMethod()`や`t.field`を呼んでも、`Bottom`ではなく`Top`側のものが使われます。

</details>

## 問題10

親クラスのコンストラクタが`private`しかない場合、別クラスからこの親クラスを`extends`して、明示・暗黙どちらの方法でも`super()`を呼び出せますか？

<details><summary>解答</summary>

**呼び出せません。**たとえ同じパッケージ内であっても、`private`なコンストラクタは宣言されたクラスの中だけでしか呼べないため、サブクラス側からの`super()`（明示的に書いても、書かずに自動生成されても）は必ずコンパイルエラーになります（「コンストラクタはprivateアクセスされます」）。

</details>

## 問題11

`record`の`equals()`と`toString()`は、どんな挙動になりますか？普通のクラス（未オーバーライド）と何が違いますか？

<details><summary>解答</summary>

**recordの`equals()`は自動生成され、コンポーネント（フィールド）の中身を比較します。**普通のクラスで未オーバーライドの`equals()`が`==`と同じ参照比較になるのとは対照的です。`toString()`も自動生成され、`ClassName[component1=値1, component2=値2]`という形式になります（例：`Food[name=Snack]`）。

</details>

## 問題12

インターフェースの抽象メソッドが`CharSequence x();`と宣言されているとき、実装クラスで`public Object x() { ... }`のようにオーバーライドできますか？

<details><summary>解答</summary>

**できません。**「戻り値の型ObjectはCharSequenceと互換性がありません」というコンパイルエラーになります。オーバーライドの戻り値は「同じ型」か「より狭い型（サブタイプ）」にしか変更できません（共変戻り値）。`Object`は`CharSequence`の**スーパータイプ**なので、逆方向への変更は認められません。

</details>

## 問題13

`int d = 1;`のとき`method(Double x, float y)`という多重定義に`d`を渡せますか？もし`double d = 1;`だったらどうですか？

<details><summary>解答</summary>

**`int`の場合は渡せません**が、**`double`の場合は渡せます。**`int`から`Double`への変換は「`int→double`（ワイドニング）＋`double→Double`（ボクシング）」という2段階の組み合わせが必要になり、Javaのメソッド呼び出し変換ルールはこれを1回の変換として認めません。`double`であれば`double→Double`のボクシング1段階だけで済むので、こちらは候補に入ります。

</details>

## 問題14

switch式で`default`を省略できるのは、どんなときですか？

<details><summary>解答</summary>

**enum型のswitch式で、全てのenum定数をcaseに書き切っている場合だけです。**`int`や`String`が対象の場合は、理論上すべての値を列挙できないため、switch式では常に`default`が必須です（省略すると「switch式がすべての可能な入力値をカバーしていません」というエラー）。なお**switch文**（式ではなく文として書く場合）は、そもそも網羅性が要求されないので`default`は常に省略可能です。

</details>

マルチキャッチ（`catch (A | B e)`）の変数`e`に対して、catchブロックの中で`e = 何か新しい値;`のように再代入できますか？

## 問題16

`interface Y extends X`、`class One implements Y`（`One`は`X`を間接的にしか実装していない）というとき、`One`の中から`X.super.calculate()`のように書けますか？

<details><summary>解答</summary>

**書けません。**「Xは内部クラスを囲みません」というコンパイルエラーになります。`InterfaceName.super.method()`が使えるのは、そのクラスが**直接**`implements`／`extends`している相手だけです。`One`は`Y`を直接実装していても`X`は間接的な関係でしかないため、`X.super`は使えません。

</details>

## 問題17

`static void main(...)`の中に直接`X.super.calculate()`と書けますか？`Main`が`X`を直接implementsしていた場合はどうですか？

<details><summary>解答</summary>

## 問題18

2つのインターフェースが同じシグネチャの`default`メソッドを持ち、1つのクラスが両方implementsして衝突（ひし形問題）が起きているとき、片方を`abstract`にすれば解決しますか？

<details><summary>解答</summary>

**解決しません。**片方を`abstract`（本体なし）にしても、もう片方が`default`のままだと「abstractでなく、オーバーライドしません」というエラーのままです。解決するのは片方を**`private`または`static`**にした場合だけです。理由は、`private`・`static`は「外部に公開される継承可能なインスタンスメソッド」として数えられないため、実装クラスから見ると`default`を持っているのは残った片方だけになり、衝突相手がいなくなるからです。

</details>

## 問題19

自分で作ったクラスで`toString()`をオーバーライドするとき、書き方で気をつける点は何ですか？

<details><summary>解答</summary>

**戻り値は`String`型、アクセス修飾子は`public`にする必要があります。**`Object`の`toString()`が`public String toString()`と宣言されているため、オーバーライドはこれと同じシグネチャ（引数なし・戻り値`String`）にし、アクセス修飾子は同じか、より広くする必要があります（`public`より狭い`protected`や未指定にするとコンパイルエラー）。何もオーバーライドしないと`Object`のデフォルト実装（`クラス名@ハッシュコード`の16進数）がそのまま使われ、フィールドの中身は反映されません。

</details>

## 問題20

`Float[] f2 = new float[]{1.0F};`はコンパイルできますか？理由も教えてください。

<details><summary>解答</summary>

## 問題21

`float[] arr = {1, 2, 3};`（中身は`int`リテラル）はコンパイルできますか？問題20との違いも教えてください。

<details><summary>解答</summary>

## 問題22

`Float[] a = {1.0};`（`double`リテラル）や`Float[] a = {1};`（`int`リテラル）はコンパイルできますか？

<details><summary>解答</summary>

## 問題23

`Integer i = null;`のあと`int x = i;`のように使うと、どうなりますか？`Boolean`など他のラッパークラスでも同じですか？

<details><summary>解答</summary>

**`NullPointerException`が発生します。**アンボクシング（ラッパー型→プリミティブ型への変換）は、参照が指す先の値を取り出す処理なので、参照が`null`の状態でアンボクシングしようとすると必ずNPEになります。これは`Integer`に限らず、`Boolean`（例：`if (b)`のような条件式での暗黙アンボクシング）など、**どのラッパークラスでも共通のルール**です。

</details>

## 問題24

`"Hello".endsWith("llo")`のように、`endsWith()`の引数が2文字以上の場合、判定はどうなりますか？「最後の1文字だけを見る」という理解は正しいですか？

<details><summary>解答</summary>

**引数の長さに関わらず、末尾からその文字列全体と一致するかを判定します。**「最後の1文字だけ」という理解は不正確です。`"Hello".endsWith("llo")`は`true`（末尾3文字が一致）、`"Hello".endsWith("Hello")`も`true`（文字列全体と一致）になります。引数が1文字の場合にたまたま「最後の1文字が合っているか」と同じ結果になるだけです。`startsWith()`も同様に、先頭から任意の長さの文字列と一致するかを見ます。

</details>

## 問題25

親クラスに`public List<Number> test(Set<CharSequence> s)`というメソッドがあります。サブクラスでこれを引数`Set<String> s>`・戻り値`List<Integer>`に変えて再定義すると、どうなりますか？また、引数を`TreeSet<String> s`に変えた場合はどうですか？

<details><summary>解答</summary>

**`Set<String>`に変えた場合はコンパイルエラーになります。**理由は「オーバーライドにもオーバーロードにも、どちらにもなれない中途半端な状態」になるためです。`Set<String>`と`Set<CharSequence>`は消去（erasure）すると両方とも`Set`で同じなので、「型引数が違う＝オーバーライドの条件を満たさない」し、「消去型が同じ＝オーバーロードの条件（別メソッドと呼べること）も満たさない」。結果、名前の競合エラーになります。

**`TreeSet<String>`に変えた場合はコンパイル成功します。**`TreeSet`と`Set`は消去してもそもそも別の型なので、正当な独立したオーバーロードとして成立します。オーバーロードになった時点で、戻り値は元のメソッドと無関係になり、`Number`である必要すらなく完全に自由です（`List<Integer>`でも何でもOK）。

まとめると3パターン：
- 引数の消去型・型引数ともに同じ → オーバーライド。戻り値はコンテナだけ狭められる（型引数は固定）
- 引数の消去型は同じだが型引数だけ違う → **コンパイルエラー**（名前の競合、オーバーライドにもオーバーロードにもなれない）
- 引数の消去型自体が違う → 独立したオーバーロード。戻り値は完全に自由

</details>

## 問題26

`byte`同士や`short`同士を`+`で足し算すると、結果の型は何になりますか？またその理由は？`short s1 = 10 + 20;`（リテラル同士）はキャストなしでコンパイルできますか？

<details><summary>解答</summary>

**`byte+byte`でも`short+short`でも、結果は必ず`int`になります。**これは「二項数値昇格（binary numeric promotion）」というルールで、算術演算子（`+`・`-`・`*`・`/`・`%`）を使う時、`int`より小さい型（`byte`・`short`・`char`）は演算前に両方とも`int`へ昇格してから計算されるためです。根本理由は、JVMのバイトコードに`byte`/`short`専用の算術命令がそもそも存在せず、`int`の命令でしか計算できないことにあります。

**`short s1 = 10 + 20;`はキャストなしでコンパイル可能**です。これは「二項数値昇格で計算自体はintで行われる」ことと、「両辺がリテラル（コンパイル時定数）なので`10+20`が定数式として`30`に確定し、shortの範囲に収まっていればキャスト不要」という定数式の縮小変換ルールが同時に働くためです。一方`short s3 = s1 + s2;`のように**変数**同士だと、コンパイル時に値が確定しないため、int→shortの変換に明示的なキャストが必須になります。

</details>

## 問題27

インターフェースの定数（暗黙の`public static final`）は、宣言時に初期化しなくてもいいですか？普通のクラスの`final`フィールドとの違いは？

<details><summary>解答</summary>

**インターフェースのフィールドは宣言と同時に初期化が必須です。**後から代入する場所（コンストラクタ・staticイニシャライザ）が一切用意されていないため、その場で値を書く以外に方法がありません。一方、普通のクラスの`final`フィールドは、宣言時・コンストラクタ内・staticイニシャライザ内のいずれかで初期化すればよく、選択の幅があります。

</details>

## 問題28

`byte`同士・`short`同士を`+`で足し算すると、結果の型は何になりますか？また`short s = 10 + 20;`（リテラル同士）はキャストなしでコンパイルできますか？

<details><summary>解答</summary>

**`byte+byte`でも`short+short`でも、結果は必ず`int`になります。**「二項数値昇格」というルールで、算術演算子を使う時`int`より小さい型（`byte`・`short`・`char`）は演算前に両方とも`int`へ昇格します（JVMに`byte`/`short`専用の演算命令が無いため）。`short s = 10 + 20;`はキャストなしでコンパイル可能です。両辺がリテラルなので`10+20`が定数式として`30`に確定し、shortの範囲に収まっていればキャスト不要というルールが働くためです。ただし`short s3 = s1 + s2;`のように**変数**同士だと、コンパイル時に値が確定しないためキャストが必須になります。

</details>

## 問題29

`substring(start, end)`と`replace(start, end, str)`で、`end`が文字列長を超えた場合の挙動に違いはありますか？

<details><summary>解答</summary>

**あります。**`substring()`（String・StringBuilder共通）は`end`が文字列長を超えると`StringIndexOutOfBoundsException`が発生します（クランプされない）。一方`StringBuilder`の`replace()`は`end`が文字列長を超えても自動的に`length()`にクランプされ、例外にはなりません。同じ「`end`が範囲外」という状況でも、メソッドによって挙動が違う点に注意が必要です。

</details>

## 問題30

ジェネリクスの引数で、コンテナ型（`List`/`ArrayList`など）と型パラメータ（`<>`の中身）、どちらが変えられますか？

<details><summary>解答</summary>

**コンテナ型は先祖型ならOK（普通のポリモーフィズム）、型パラメータは完全固定で変えられません（不変）。**例えば`ArrayList<String>`を受け取る引数は`List<String>`や`Collection<String>`でもよいですが、`<String>`の部分だけは変更不可です。継承階層は`Object`→`Iterable`→`Collection`→`List`→`ArrayList`（`ArrayList`が一番具体的）で、`ArrayList`は`List`を「持っている（has-a）」のではなく「`ArrayList`は`List`である（is-a）」という向きが正しいです。

</details>

## 問題40

2次元配列を`clone()`した時、「外側」と「内側」でコピーされ方はどう違いますか？（`clone()`は浅いコピー＝シャローコピー）

<details><summary>解答</summary>

**外側（一番上の配列自体）は完全に別物になりますが、内側（中に入っている配列）は同じ実体を指したまま共有されます。**検証済み：

```java
char[][] array1 = {{'a', 'b'}, {'c', 'd'}};
char[][] array2 = array1.clone();
char[] array3 = array1[1].clone();

array1 == array2                : false  // 外側は別物
array1[1] == array2[1]          : true   // 内側は同じ実体を共有（シャローコピー）
array1[1] == array3             : false  // array1[1]自体をcloneすると、これは別物になる
array1.equals(array2)           : false  // 配列はequals()を独自定義していないので==と同じ扱い
array3[0] == array1[1][0]       : true   // char(基本データ型)の値そのものはコピーされているので値は一致
array2[0] == array1[0]          : true   // 内側の参照は共有されているので、その先の中身(char)も当然一致
```

イメージ：`char[][]`は「`char[]`を複数個入れた入れ物」。`array1.clone()`は**入れ物だけ**を新しく作り直しますが、中に入っている「どの配列を指しているか」という参照はそのままコピーするので、`array1[1]`と`array2[1]`は同じ実体を指します（`==`で比較すると参照比較になるのでtrue）。

一方`array1[1].clone()`は、その中身の1次元配列そのものをcloneしているので、こちらは全く新しい実体（`array3`）が作られます。ただし中の`char`の値自体はコピーされているので、値としては元と一致します（`array3[0] == array1[1][0]`はtrue。これは基本データ型どうしの値比較であって、オブジェクトの参照比較ではない点に注意）。

**まとめ：`clone()`で外側（配列自体）を比較すると別物（false）になり、内側（さらにその先の実体・値）を辿って比較するとtrueになる、というのがシャローコピーの本質。**

</details>

## 問題47

`Number calc();`を`public int calc()`（プリミティブ型）でオーバーライドしようとすると、`int`は自動的に`Integer`になって`Number`に収まりますか？　また「オートボクシングが効かない」のは戻り値全般の話ですか？

<details><summary>解答</summary>

**オーバーライドの成立判定では、`int`→`Integer`という変換は一切考慮されません。**検証済み：

```java
sealed interface Shape permits Rectangle {
    Number calc();
}
record Rectangle(int height, int width) implements Shape {
    public int calc() { return height * width; }
}
```
→
```
Rectangleのcalc()はShapeのcalc()を実装できません
戻り値の型intはNumberと互換性がありません
```

コンパイラは「宣言されている`int`という型」と「`Number`という型」を直接比較するだけで、`int`はプリミティブ型なので継承関係（クラス階層）自体を持たず、`Number`のサブタイプにはなり得ません。

**ただし「戻り値だからオートボクシングが効かない」という一般化は広すぎます。** オーバーライドが絡まない普通のメソッドなら、`return`文の中身は普通にオートボクシングされます（検証済み）：

```java
static Number calc() {
    return 5;   // intをNumberとして返す。普通にコンパイル成功
}
```

同様に代入や引数渡しでも普通に効きます（`Number n = 5;`、`list.add(5)`など、どちらもOK）。

**正確な境界線**：
- **値を実際に変換して収める場面**（代入・引数渡し・return文の中身）→ オートボクシングが効く
- **2つのメソッドの「宣言された戻り値の型」どうしを、値の変換を考慮せず型のまま比較する場面（オーバーライドの成立判定）**→ オートボクシングは一切考慮されない

「静的型だから」でも「戻り値だから」でもなく、**「オーバーライドの型チェックという、値ではなく型の宣言だけを機械的に比較する特殊な場面」だけ、オートボクシングが効かない**、というのが正確な理解。

</details>

## 問題48

`protected`なメソッドへのアクセス可否は、静的型（宣言型）と実体（実行時の型）のどちらで判定されますか？また、アクセスが通った後で実際に呼ばれる実装（動的束縛）は、protectedという修飾子によって何か変わりますか？

<details><summary>解答</summary>

**アクセス可否は静的型だけで判定され、動的束縛（実際にどの実装が動くか）はprotectedかどうかに関係なく実体で決まります。**この2つは完全に別レイヤーの話です。

まずアクセス可否が静的型基準であることの検証：

```java
package p1;
public class A {
    protected void hello() { System.out.println("A"); }
}
package p2;
public class B extends A {
    void test() {
        A ref = new B();   // 静的型：A、実体：B
        ref.hello();        // コンパイルエラー
    }
}
```
→ `hello()はAでprotectedアクセスされます`

実体が確かにBのインスタンスでも、`ref`の**宣言型がA**である以上アクセス不可でした。`protected`を別パッケージのサブクラスから使うには、参照の**静的型がサブクラス自身（またはその先）**である必要があります（`A ref`ではなく`B ref`にすれば通る）。

次に、コンパイルを通った呼び出しが実際にどの実装を動かすかは、通常のオーバーライドと全く同じく動的束縛に従うことの検証：

```java
protected void hello() { ... }         // A：大元の宣言
@Override protected void hello() {...}  // B extends A
@Override protected void hello() {...}  // C extends B

B ref = new C();   // 静的型：B、実体：C
ref.hello();         // → "Cのhello"
```

`hello()`が`protected`だろうが`public`だろうが、動的束縛の仕組み自体には一切影響しません。

| 観点 | 何で決まる | protected/publicで変わるか |
| --- | --- | --- |
| アクセス可否（コンパイルエラーになるか） | 参照の**静的型** | **変わる**（protectedは同パッケージ or サブクラス自身の型経由が必須） |
| どの実装が動くか（動的束縛） | オブジェクトの**実体** | **変わらない**（アクセス修飾子に関係なく常にオーバーライド優先） |

</details>

## 問題49

`private`メソッドと`static`メソッドは、動的束縛（オーバーライドによるポリモーフィズム）の対象になりますか？

<details><summary>解答</summary>

**どちらも動的束縛の対象になりません。**検証済み：

```java
class A {
    private void hello() { System.out.println("Aのprivate hello"); }
    public void callHello() { hello(); }

    public static void staticHello() { System.out.println("Aのstatic hello"); }
}
class B extends A {
    private void hello() { System.out.println("Bのprivate hello"); }
    public static void staticHello() { System.out.println("Bのstatic hello"); }
}

A ref = new B();
ref.callHello();    // → "Aのprivate hello"
ref.staticHello();  // → "Aのstatic hello"
```

- **`private`メソッド**：`B`の`hello()`はAの`hello()`を**オーバーライドしていません**（`private`メソッドはサブクラスから見えず、継承・オーバーライドの対象外）。`A`と`B`それぞれが独立した別物の`private hello()`を持っているだけなので、`A.callHello()`は常に自分（`A`）の`private hello()`を呼びます。実体が`B`かどうかは無関係です。
- **`static`メソッド**：`B`の`staticHello()`はAの`staticHello()`を**オーバーライドではなく「隠蔽（hiding）」**しています。static メソッド呼び出しは、インスタンスメソッドと違って**参照の静的型（宣言型）だけでコンパイル時に確定**するため、`ref`の静的型が`A`である以上、実体が`B`でも常に`A`側の`staticHello()`が呼ばれます。

動的束縛が起きるのは、あくまで「オーバーライド可能なインスタンスメソッド」だけです。`private`（継承・オーバーライド不可）と`static`（クラスに紐づくメンバーで、インスタンスのポリモーフィズムの対象外）は、どちらも仕組みの前提からして動的束縛の対象になり得ません。

</details>

## 問題50

`private`メソッドがサブクラスから完全に見えない（隠蔽されている）とすると、サブクラス側で全く同じ名前・シグネチャのメソッドを、今度は`public`などのアクセス修飾子で定義することはできますか？それは「オーバーライド」として扱われますか？

<details><summary>解答</summary>

**定義できます。ただしそれは「オーバーライド」ではなく、完全に独立した「新規メソッド」として扱われます。**検証済み：

```java
class A {
    private void hello() { System.out.println("Aのprivate hello"); }
}
class B extends A {
    public void hello() { System.out.println("Bのpublic hello"); }   // @Overrideなし
}
```
→ 普通にコンパイル成功、`new B().hello()`で"Bのpublic hello"が出力される。

ここで`B`の`hello()`に`@Override`を付けてみると：

```java
class B2 extends A2 {
    @Override
    public void hello() { ... }
}
```
→ `メソッドはスーパータイプのメソッドをオーバーライドまたは実装しません`というコンパイルエラー。

これが決定的な証拠で、コンパイラ自身が「これはオーバーライドではない」と明言しています。`private`メソッドはサブクラスに継承されず、そもそもサブクラスから見ると**存在しないのと同じ**扱いになるため、`B`が同じ名前で`hello()`を宣言しても、それは「`A`の`hello()`を上書きしている」のではなく、「`A`には一切関係のない、`B`というクラスに新しく生まれたメソッド」という扱いになります。アクセス修飾子を`public`のように広くしても、この関係は変わりません（そもそも上書きする相手が見えていないので、狭い/広いという比較自体が発生しない）。

</details>
