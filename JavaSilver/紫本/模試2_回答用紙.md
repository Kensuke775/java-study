### 問題5
- `String.toString()` は自分自身(`this`)を返すだけで新規オブジェクトを生成しない。生成元がリテラルでも`new String(...)`でも同じ。
- `intern()` も文字列プール内の既存参照を返すだけで新規生成しない。
- `StringBuilder.toString()` はStringBuilder自体がString型ではないため、呼ぶたびに内部データから新規Stringオブジェクトを生成する（同じStringBuilderに対して複数回呼んでも毎回別オブジェクト、`==`はfalse）。

### 問題7
```java
String str = "Japan";
StringBuilder sb = new StringBuilder("Japanese");
str.replace("pan", "va");         // (A)
sb.substring(0, 5);               // (B)
sb.replace(2, 8, "va");           // (C)
System.out.println(str.equals(sb));
```
- `String.replace()` はイミュータブルなStringの**新しい値を返すだけ**。戻り値を受け取らないと何も起きない → `str`は`"Japan"`のまま変化なし。
- `StringBuilder.substring()` も**新しいStringを返すだけ**でStringBuilder自体は変更しない → `sb`は`"Japanese"`のまま変化なし。
- `StringBuilder.replace()` だけは**自分自身を書き換える**破壊的メソッド → `sb`が`"Japanese"`→`"Java"`に変化。
- `String.equals(Object)` は引数が`instanceof String`でなければ問答無用で`false`。`sb`はStringBuilderなので中身が同じでも常に`false`。
- 正解：E（`false`）。

### 問題12
```java
ArrayList<String> code = new ArrayList<>(List.of("AU", "GB", "JP", "US"));
show(code);
private static void show( [ (1) ] ) {
    for (String s : list) System.out.print(s + ":");
}
```
- 正解：B, E（`List<String> list` / `Collection<String> list`）

**継承関係（矢印の向き）**
```
Iterable  ←  Collection  ←  List  ←  ArrayList
（一番上＝抽象・先祖）              （一番下＝具体的・子）
```
`ArrayList`が`List`を`extends`しているのではなく`implements`しているだけだが、矢印の向き（先祖←子）はこの並びで固定。`ArrayList`が一番下＝一番具体的な型で、`Iterable`が一番上＝一番抽象的な型。

**今回の要点**
- 仮引数の型は`Iterable<String>`/`Collection<String>`/`List<String>`/`ArrayList<String>`の**どれでもOK**（`ArrayList`が全部の資格を実装＝is-aしているため）。ただし型パラメータ`<String>`だけは4つとも共通で変更不可。
- 「`ArrayList`は`List`を持っている（has-a）」ではなく「`ArrayList`は`List`である（is-a）」という向きが正しい。実体は常に1個の`ArrayList`オブジェクトで、参照する型が変わるだけ（`String s = "hello"; Object o = s;`とまったく同じ構造）。
- この「先祖型の変数で受け取れる」という話は**「共変(covariance)」ではなく普通の多態性（is-a関係）**。「共変」という用語は配列（`Number[] n = new Integer[3];`）やオーバーライドの戻り値の話専用で、ジェネリクスの型引数はむしろ逆に**不変（invariant）＝`<String>`は変えられない**という、混同しやすいが別軸の話。
- ダイヤモンド`<>`は`new`する時専用の省略記法で、型の宣言（変数・引数の型）には使えない（`List<> list`は構文エラー）。
- 型パラメータなしの生の型（`List list`）は構文上は通るが、要素が`Object`扱いになり、拡張for文で`String s`と明示的に受けている箇所で不一致エラーになる。
- `Object`クラスはそもそも型パラメータの仕組みを持たないため、`Object<String>`のような指定はできない。

### 問題23（正解：C）
```java
public sealed interface Item permits Food, Drink {}
// Food/Drinkをどう宣言すればコンパイルが通るか
```

**見極めチェックリスト**
1. `permits`に書かれた型は**直接**implements/extendsが必要（他の許可された型経由の間接継承では不可）
2. `sealed`の直接のサブタイプは`final`／`sealed`／`non-sealed`のいずれか1つが必須（**recordは暗黙finalなので省略可**）
3. `non-sealed`自身に`permits`は書けない（意味が矛盾するため構文エラー）
4. `sealed`は原則`permits`必須（**同一ファイル内に全サブタイプが揃っている場合のみ省略可**、別ファイルなら必須）
5. interfaceには`final`を付けられない
6. インターフェース同士の継承は`extends`（`implements`ではない）

**正解C**：
```java
public sealed interface Item permits Food, Drink {}
non-sealed interface Food extends Item {}
record Drink() implements Food, Item {}
```
`Drink`が`Food`と`Item`の**両方**を直接implements（①クリア）。`Food`経由で間接的にItemを継承していても、`permits`のルール上は`Item`も明示的に直接implementsする必要がある（「重複継承」に見えるが必須の記述）。recordなので暗黙final（②クリア、指定不要）。

**誤りの選択肢はそれぞれ1つずつルール違反**：
- A：`Drink`が`Food`だけimplementsし`Item`を直接実装していない（①違反）
- B：interface`Drink`が`Food`を`implements`と誤記（⑥違反、`extends`が正しい）
- D：`Food`が`non-sealed`なのに`permits`も指定（③違反）
- E：interfaceの`Food`に`final`（⑤違反）、`Drink`が`sealed`なのに`permits`なし（④違反）

### 問題30（正解：B, E）
```java
String text = " Lime Lemon ";
text = text.trim();   // "Lime Lemon"（前後の空白だけ除去、間の空白は残る。10文字）
```
- `trim()`は前後の空白のみ除去（間の空白は除去しない）
- `indexOf("m")` → 2（先頭から探索）、`indexOf("m", 4)` → 7（index4以降だけを探索、それより前の一致は無視）
- `contains(CharSequence)` は大文字小文字を区別し、部分一致すれば`true`
- `==`による参照比較は、内容が同じでも別オブジェクトなら`false`（Dの誤りはこれ）

**`trim`/`substring`/`concat`/`replace`共通の重要ルール**：
- **内容が変化しない場合**：最適化により**`this`（呼び出し元と同一オブジェクト）を返す** → `==`は`true`
  ```java
  whole == whole.substring(0)            // true（全体を取るだけ＝変化なし）
  whole == whole.concat("")              // true（空文字追加＝変化なし）
  whole == whole.replace("z","Z")        // true（該当箇所なし＝変化なし）
  ```
- **内容が変化する場合**：**毎回新規オブジェクトを生成**する。**同じソースから複数回呼んでも、呼ぶたびに別オブジェクト**（結果はキャッシュされない）
  ```java
  String source = " Lime Lemon ";
  String a = source.trim();
  String b = source.trim();
  a == b        // false（同じsourceから2回trimしても別オブジェクト）
  a.equals(b)   // true（中身は同じ）
  ```
- 例外：`String.toString()`だけは変換自体が発生しないため、無条件で常に`this`を返す（上記の「変化の有無で分岐する」ルールとは別枠）

### 問題39（正解：D）— instanceofパターン変数のスコープ

**基本ルール**：`!(obj instanceof Type v)`のように**否定した条件**の場合、ifブロックの中で**必ずそこで処理が終わる**（`throw`/`return`など）と保証できれば、`v`はその**if文の外（それ以降のコード全体）**でも使える。一方`else`ブロックだけで完結させた場合は、`v`が使えるのは**そのelseブロックの中だけ**。

```java
// パターンA：throwで抜ける → if文の外でも使える
if (!(obj instanceof String s)) {
    throw new RuntimeException();
}
System.out.print(s);   // OK

// パターンB：elseだけ → elseの中でしか使えない
if (!(obj instanceof String s)) {
} else {
    System.out.print(s);   // OK（elseの中）
}
System.out.print(s);   // ← コンパイルエラー（elseの外）

// throwを外すと、ifの中に処理を書いても未代入の可能性が残るためエラーになる
if (!(obj instanceof String s)) {
    System.out.println("not a string");   // returnもthrowもない
}
System.out.print(s);   // ← シンボルを見つけられませんエラー
```

**return/else/throwを組み合わせた実例**（検証済み、コンパイル・実行OK）：
```java
public class Main {
    public static void main(String... args) {
        try {
            validate("Java");                          // (A)
            validate(17);                              // (B)
        } catch (RuntimeException e) {
            e.printStackTrace();
        }
    }
    private static void validate(Object obj) {
        if (obj instanceof Integer o) {
            System.out.print("Integer ");
        }
        if (!(obj instanceof String s)) {
            return;
        } else {
            System.out.print(s);
        }
        if (!(obj instanceof String b)) {
            throw new RuntimeException("Ex ");
        }
        System.out.print("String ");
        System.out.print(s + b);
    }
}
```

**例外の伝播について**：チェック例外・非チェック例外どちらも、投げた瞬間にプログラムが終了するわけではない。投げたメソッドの残りの処理はスキップされるだけで、キャッチされるまで呼び出し元へ伝播していき、キャッチされた後は普通に処理が続く。

### 問題43（正解：B）— forループ内でスローされた例外の伝播
```java
String[] list = {"Mon", "Sat", "Friday", "Day", "Sun"};
try {
    execute(list);
} catch (DataTooLongException | InvalidDataException ex) {
    ex.getMessage();   // 呼ぶだけで結果はどこにも出力していない
}
public static void execute(String[] l) throws DataTooLongException, InvalidDataException {
    for (var s : l) {
        switch (s) {
            case "Mon", ... -> System.out.print("Open ");
            case "Sat", "Sun" -> System.out.print("Close ");
            case "Monday", ..., "Friday", ..., "Sunday" -> throw new DataTooLongException(s + " ");
            default -> throw new InvalidDataException(s + " ");
        }
    }
}
```
実行結果：`Open Close`（検証済み）

- "Mon"→"Open "、"Sat"→"Close "、3つ目の"Friday"で`DataTooLongException`をスロー
- **`execute()`メソッドの中にはcatchが一切無い**ため、スローされた時点で**forループも`execute()`メソッド自体も丸ごと抜けて**、呼び出し元`main()`の`catch`まで一気に伝播する（"Day"・"Sun"は処理されない）
- `main()`側で`ex.getMessage()`を呼ぶだけで、結果はどこにも出力していないので、それ以上の出力はない

**一般化した例外伝播ルール**：スローされた場所から見て、**一番近い「対応するcatch」を探す**。それが同じメソッド内（forループの中など）にあれば、そこでキャッチされて**処理は続行**できる。同じメソッド内のどこにも対応するcatchが無ければ、**そのメソッド自体を丸ごと抜けて**、呼び出し元へ伝播する。

```java
// ループの中にtry-catchがある場合 → 該当イテレーションだけスキップしてループは続行できる
for (String s : list) {
    try {
        if (s.equals("Friday")) throw new RuntimeException("bad");
        System.out.print(s + " ");
    } catch (RuntimeException e) {
        System.out.print("[skip] ");
    }
}
// 実行結果：A [skip] B C （ループ自体は最後まで回る）
```
問題43はこのケースとは逆で、`execute()`内に一切catchが無かったため、forループごとメソッドごと即座に抜けた、という違い。

### 問題46（正解：C）— switchのcaseラベルとビット演算子
```java
int i = 1; final int j = 5;
var x = 5;
switch (x) {
    case 3 & 5: yield "B";                  // 3&5はビット演算子、変数ではない
    case i: yield "C";                      // ← iはfinalが無い変数なのでコンパイルエラー
    case j: yield "D";                      // jはfinalなので定数扱い、OK
    default: throw new RuntimeException();
}
```
```
エラー: 定数式が必要です
                case i: yield "C";
```

- `case`ラベルに書けるのは**リテラル・final変数・定数式（計算結果が確定するもの）**だけ。**finalが付いていない普通の変数は不可**（今回`case i:`だけがエラー原因）
- `3 & 5`は「3と5という2つのcase値」ではなく、**ビット論理積（AND）演算の結果**（`3=0011`, `5=0101` → `AND=0001=1`）。リテラル同士の演算なので定数式として合法（検証済み：`3 & 5 = 1`）
- ビット演算子まとめ（`3`と`5`の場合）：
  - `&`（AND、両方1の時だけ1）→ `3 & 5 = 1`
  - `|`（OR、どちらか1なら1）→ `3 | 5 = 7`
  - `^`（XOR、異なる時だけ1）→ `3 ^ 5 = 6`

### 問題53（正解：D）— キャストの本質と3階層の継承チェーン

```java
class Product {}
class Book extends Product {}
class EBook extends Book {}
class Clothes extends Product {}

Product p = new Book();
System.out.print(hasBook(p) && hasEBook(p));        // 8行目
p = new Clothes();
System.out.print(hasClothes(p));                     // 10行目
p = new EBook();
System.out.print(!(hasClothes(p)) && hasEBook(p));   // 12行目
Product b = (Book)p;                                 // 13行目
if(hasEBook(p)) System.out.print(true);              // 14行目
if(hasClothes(p)) System.out.print(true);            // 15行目
```
実行結果：`falsetruetruetrue`（検証済み）

継承関係：
```
        Product
        /      \
     Book      Clothes
      |
    EBook
```

**13行目`Product b = (Book)p;`のポイント**：
- `p`の実体（動的な型）は11行目以降ずっと`EBook`のまま。この行は`p`自体を書き換えていない
- `EBook`は`Book`の子孫なので、`(Book)p`というダウンキャストは成功する（`ClassCastException`は発生しない＝選択肢Aが誤りである理由）
- 結果を代入した`b`も宣言型は`Product`のまま。「実体はEBook、宣言型はProduct」という状態は変わらない
- あえて中間の`Book`にキャストしているのは、「3階層の継承チェーンのうち、途中の型へのダウンキャストも成功する」ことを試すため（`Product`にキャストしても何もテストにならない）

**キャストの本質（この問題を通して整理した考え方）**：
- キャストは**実体を書き換えない**。変わるのは「その式の中だけ、コンパイラにどの型として扱うことを許可するか」という一時的な“切符”のようなもの
- コンパイラは変数の**宣言型（静的型）だけ**を見てメソッド呼び出しの可否を判断する。実体にそのメソッドが存在していても、宣言型経由で見えなければ呼び出せない
  ```java
  ProductW p = new BookW();
  p.getISBN();              // コンパイルエラー（Productにgetisbnは無い）
  ((BookW) p).getISBN();    // キャストすればOK
  ```
- **アップキャスト**（Book→Productのように上位へ）：常に安全、暗黙的にできる
- **ダウンキャスト**（Product→Bookのように下位へ）：明示的なキャストが必須。実体が本当にその型（かその子孫）であれば成功し、違えば`ClassCastException`
- キャストが成功するかどうかは「**実体の継承チェーン上に、キャスト先の型が含まれているか**」で決まる（実体そのものと完全一致する必要はない）
  ```java
  Product p = new EBook();
  (Product)p, (Book)p, (EBook)p  // 継承チェーン上なので全部成功
  (Clothes)p                     // 継承関係に無いのでClassCastException
  ```
- 変数を**共通の先祖型（Product）で宣言しておく**からこそ、その子孫（Book・EBook・Clothes）のどれでも自由に代入し直せる（ポリモーフィズムの基本パターン）
  - `|`（OR、どちらか1なら1）→ `3 | 5 = 7`
  - `^`（XOR、異なる時だけ1）→ `3 ^ 5 = 6`
