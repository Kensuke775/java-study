**✴︎を付けた問題の振り返り**：7-4, 7-5, 7-9, 7-15に付けたが、いずれも正解。

- **7-4（parseIntにnull）**：`NullPointerException`ではなく`NumberFormatException`（"Cannot parse null string"）です。だからBの`NumberFormatException`と、その親のDの`RuntimeException`で捕まります。なお`null`の`String`変数を`println`に渡しても、NPEにならず`null`と出ます。
- **7-5（変数のスコープ）**：はい、try / catch / finallyは別々のスコープです。tryで宣言した変数は、catchからもfinallyからも見えません。catchの引数`e`はfinallyから見えず、try-with-resourcesの変数もcatchから見えません。共有したい変数はtryの前で宣言します。各ブロックで同じ名前を宣言し直すのは問題ありません。
- **7-9（ClassNotFoundException）**：非チェック例外ではなく、**チェック例外**です。`Exception`→`ReflectiveOperationException`→`ClassNotFoundException`の順で、`RuntimeException`の子ではありません。
  - `throw new ClassNotFoundException()`を`throws`も`catch`も無しで書くと、コンパイルエラーになります。
  - Dが通るのは非チェックだからではなく、`throws`**には実際に投げない例外を書いてもエラーにならない**からです。
  - `catch (ClassNotFoundException e)`のほうは、tryの中で投げられないとエラーになります（「対応するtry文の本体ではスローされません」）。`throws`と`catch`で扱いが違います。
- **7-13（throwsのオーバーライド）**：「ゆるく」だとどちらの意味にも取れます。「広げるのはNG、同じか狭めるのはOK」と覚えると安全です。「本人かサブタイプか、それ以外は非チェック例外」という整理は合っています。CNFEも対象外で合っています。


| 選択肢                        | 親の`throws FileNotFoundException`との関係 | 結果  |
| -------------------------- | ------------------------------------ | --- |
| A（throwsなし）                | 狭い（なし）                               | OK  |
| B `ClassCastException`     | 非チェック例外なので自由                         | OK  |
| C `FileNotFoundException`  | 同じ                                   | OK  |
| D `ClassNotFoundException` | 兄弟（無関係のチェック例外）                       | エラー |
| E `IOException`            | 親（広い）                                | エラー |


FNFEは`IOException`の子、CNFEは`ReflectiveOperationException`の子で、両方とも`Exception`の子どうしです。Dのエラーは「オーバーライドされたメソッドはClassNotFoundExceptionをスローしません」と出ます。

兄弟の日チェック例外は幾つ重なってもOK

- **7-16（message と cause）**：`new FirstException("First")`のmessageは`"First"`で合っています。`new FirstException()`のcauseは、オブジェクト自身ではなく`null`です（messageも`null`）。`new FirstException(cause)`は、causeに渡した`Throwable`が入り、messageはその`toString()`になります。Eなら、causeは内側の`FirstException`で、messageは`"FirstException: First"`です。 この問題の肝は、コンストラクタが継承されないことです。`SecondException`は`(Throwable)`版しか持たないので、Cの`new SecondException("Second")`（「StringをThrowableに変換できません」）も、Dの`new SecondException()`（「引数がありません」）も作れません。

## 7-4のメモ「parseXxx()系のエラーは基本NFEですかね」

数値を作る `parseXxx` は、基本NFE（`NumberFormatException`）で合っています。ただし例外が2つあるので、実際に実行して確かめました。


| 呼び出し                                                 | 結果                |
| ---------------------------------------------------- | ----------------- |
| `Integer.parseInt("abc")`                            | NFE               |
| `Integer.parseInt("")`                               | NFE               |
| `Integer.parseInt(" 1")`（空白付き）                       | NFE               |
| `Integer.parseInt(null)`                             | NFE               |
| `Long.parseLong(null)`                               | NFE               |
| `Byte.parseByte("200")`（範囲外）                         | NFE               |
| `Double.parseDouble("abc")`                          | NFE               |
| `Double.parseDouble(null)`                           | **NPE**           |
| `Float.parseFloat(null)`                             | **NPE**           |
| `Boolean.parseBoolean("abc")` / `parseBoolean(null)` | **例外なし**（`false`） |


- `parseInt`・`parseLong` などの整数系は、`null` でもNFEになります。
- `parseDouble`・`parseFloat` は、`null` のときだけNPEになります。
- `parseBoolean` は何を渡しても例外を投げません。

7-4は `Integer.parseInt(null)` なので、NFEが飛びます。NFEの親は `IllegalArgumentException`、その親が `RuntimeException` です。

- **B**（`NumberFormatException`）：NFEそのものなので、キャッチできます。
- **D**（`RuntimeException`）：NFEの親なので、キャッチできます。
- **C**（`NullPointerException`）：NPEは飛ばないので、キャッチされません。
