ex4

コンパイルのみ javac Main.java
実行のみ　java Main(public static void main(String[] args)が入ったクラス名)
ソースファイルモードのみ java Main.java

javac Main.java → コンパイルのみ（.classファイルが作られるだけで実行はされない）
java Main → 実行のみ（既に.classがある前提で、クラス名を指定して実行）
java Main.java → コンパイル＋実行を1発で（ソースファイルモード）

コンパイルファイルを作る→javac -d bin *.java

以下で実行する↓
1 - java -classpath com.x.Main　失敗　例外処理になる。
2 - java -classpath bin com.x.Main　成功

理由は、コンパイルファイルは瓶の中に作ってあるので、パスをそのコンパイルしたファイルのパスを指定しなきゃいけない。
1の場合、パスが揃っていないため失敗する。

ex9

使えない修飾子（トップレベルクラス）
private：ダメ
protected：ダメ
static：ダメ

使える修飾子（トップレベルクラス）
public（省略も可＝package-private）
abstract
final
sealed（単体でのみ存在はNG） / non-sealed（サブクラスがある前提）
（非推奨ですが）strictfp
なぜprivate/protected/staticがダメなのか
これらは本来「ネストされた（他のクラスの中にある）クラスやメンバー」のためのアクセス制御・所属を表す修飾子です。

private/protected：誰から見えるかを制限する修飾子だが、トップレベルクラスは元々「同じパッケージ内なら誰でも見える」か「publicで全体に見える」かの2択しかなく、private（自分のクラスの中だけ）やprotected（サブクラス＋同一パッケージ）という中間的な見え方を定義する概念自体が、トップレベルには存在しない
static：これは「外側のクラスに対する所属の仕方」（インスタンスを介さずにアクセスできる）を表すもので、外側のクラスを持たないトップレベルクラスには、そもそも「静的かどうか」を区別する意味がない
なので「privateとprotectedだけ」ではなく、staticも含めた3つが使えない、という理解に修正しておいてください。

varが使えない場所（全部検証済み）
場所	使えるか
クラスのフィールド（メンバ変数）	❌ 使えない
メソッドの引数	❌ 使えない
メソッドの戻り値の型	❌ 使えない
catchの例外の型	❌ 使えない
初期化子なしの宣言（var x;）	❌ 使えない
nullだけの初期化（var x = null;）	❌ 使えない（型を推論できないため）
複合宣言（var a = 1, b = 2;）	❌ 使えない
拡張for文（for (var v : arr)）	✅ 使える
通常のfor文の初期化（for (var i = 0; ...)）	✅ 使える
try-with-resources（try (var br = ...)）	✅ 使える
普通のローカル変数宣言（var x = 5;）	✅ 使える

catch (Exception e) { ... }
このExceptionの部分（例外の型）をvarに置き換えることができない、という意味です。

catch (var e) { ... }   // ← これがNG


どこの話か	varが使えるか
メソッドを定義するときの引数の型（void method(var x)）	❌ NG
呼び出す側で、渡す変数自体をvarで宣言する（var n = 5; method(n);）	✅ OK
「引数として渡せない」のではなく、「メソッド定義のシグネチャ（設計図）の中で、型の代わりにvarと書くこと」ができない、というのが正確な意味です。戻り値の型も全く同じ話で、「メソッドの定義でvar m() { return 1; }のように戻り値の型そのものをvarにする」のがNGなだけで、そのメソッドの呼び出し結果をvar result = method();のように受け取る側は問題なくvarが使えます。

ex12

    public static void maina(int[] args) {}
    public static void maina(int... args) {}

    public static void maina(int i, int[] args) {}
    public static void maina(int i, int... args) {}
    は共存できない

型としての実体：int[] argsもint... argsも、コンパイル後は完全に同一の型（[I＝intの配列）
中身の渡し方（呼び出し方の便利さ）：全く別物（int[]は配列を明示的に作って渡す、int...はバラバラの値を並べるだけで渡せる）
この2つを分けて考えると、

「型が同じ」→ だから同じクラスに同時定義すると重複エラーになる
「渡し方は違う」→ だから見た目上は別物のように感じて当然（沼にハマる原因はここ）
