# オートボクシング＋アップキャストの連鎖（問題4）

## 検証コード

```java
private static String test(Number n) {
    if (n instanceof Integer i) {
        return "C";
    }
    ...
}
String result = test(0b0110);   // int値の6を渡す
```
```
C
```
→ 検証済み。`int`が`Number`型の引数にそのまま渡せている。

## 何が起きているか：「int → Integer」→「Integer → Number」の2段階

1. **`int` → `Integer`**（オートボクシング）：`int`には`Integer`という**専用の相棒（固定ペア）**が決まっている。`Number`という参照型が期待されている以上、プリミティブのままでは渡せないので、まず対応するラッパークラスに変換される
2. **`Integer` → `Number`**（アップキャスト）：`Integer`は元々`Number`のサブクラスなので、そのまま`Number`型として扱ってよい（これが**ポリモフィズムの土台**＝「子は親として振る舞える」）

| プリミティブ | 対応するラッパークラス（固定ペア） |
|---|---|
| `int` | `Integer` |
| `long` | `Long` |
| `double` | `Double` |
| `boolean` | `Boolean` |

「`Number`型が欲しいから何かラッパーにする」のではなく、「**`int`が渡された時点で、`int`専用の相棒である`Integer`に変換される**」という決まったルール。その結果できた`Integer`が、たまたま`Number`のサブクラスだったので、そのまま収まる。

## なぜ「2段階の暗黙変換禁止」に引っかからないのか

以前確認した`Double d = Math.round(3.14);`のエラーとの違いが核心。

| | 1回目 | 2回目 | 2回目の性質 |
|---|---|---|---|
| ❌ダメな例 | `long→double`（ワイドニング） | `double→Double`（ボクシング） | **新しく型を作り変える"作業"** |
| ✅OKな例（今回） | `int→Integer`（ボクシング） | `Integer→Number`（アップキャスト） | **もう出来上がったIntegerを、ただ広い型として見るだけ（無作業）** |

## アップキャストは「実質何もしていない」（無料パス）

```java
Object o = 6;   // int → Integer(ボクシング) → Number → Object（アップキャスト2回）
System.out.println(o.getClass());   // → class java.lang.Integer
```
→ 検証済み。`Object`まで格上げしても、中身は最後まで`Integer`のまま変わらない。

- **ボクシング**：メモリ上に**新しいオブジェクトが実際に作られる**、本物の"作業"
- **アップキャスト**：オブジェクトの中身は一切変わらない。同じインスタンスを「もっと広い型のレンズ」で見ているだけ＝**カウントに入らない、無料パス**

「2段階禁止」のカウントに入るのは**プリミティブ同士のワイドニングとボクシングという“実際にデータを作り変える変換”だけ**。アップキャストは何回連鎖しても1回分にすらカウントされない。だから今回の`int → Integer → Number`は実質「ボクシング1回だけ」の扱いになり、禁止ルールには引っかからない。

## まとめ

- `int`は「`Number`だから何かのラッパーになる」のではなく、「**`int`専用の相棒`Integer`にオートボクシングされる**」→ その`Integer`がたまたま`Number`の子だったので収まる
- アップキャストは「作業」ではなく「型の見方を変えるだけ」なので、いくら連鎖しても暗黙変換の回数制限にはノーカウント
- ポリモフィズムの核心（「子は親として振る舞える」＝アップキャストが自由に効く）が、このオートボクシングの許容にもそのまま活きている
