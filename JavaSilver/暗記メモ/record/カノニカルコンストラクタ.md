# カノニカルコンストラクタ

## カノニカル（標準）コンストラクタとは

`record`ヘッダーと**全く同じ引数リスト**を持つコンストラクタのこと。何も書かなければ、コンパイラが全フィールドを代入する形で自動生成する。

```java
record Data(String value) {}
// ↓ 何も書かなくても、これが自動生成されている
// Data(String value) { this.value = value; }
```

## 追加のコンストラクタは、必ず`this(...)`でカノニカルに委譲しなければならない

ヘッダーと違う引数リストのコンストラクタ（＝追加のコンストラクタ）は、最初の文で`this(...)`を呼んでカノニカルコンストラクタに辿り着く必要がある。`super(...)`や直接のフィールド代入で済ませることはできない。

```java
record Data(String value) {
    public Data() {
        // 何も書かない
    }
}
```
```
エラー: コンストラクタが標準でないため、先頭文がクラスDataの他のコンストラクタを呼び出す必要があります
```

これは`value`フィールドが`final`で、**カノニカルコンストラクタだけが唯一その初期化を担う場所**と決まっているため。追加のコンストラクタが自由に振る舞えると「カノニカルを通さずに未初期化のままインスタンスができる」抜け道ができてしまうので、それを防ぐルール。

## `this(...)`には、カノニカルの引数型に合う値を渡す必要がある

```java
record Record(String value){
    Record(){
        this();   // ← NG
    }
}
```
```
エラー: コンストラクタの呼出しが再帰的です
```

`this()`（引数なし）は、このクラスに存在する**もう一つの引数なしコンストラクタ`Record()`＝自分自身**を呼ぶことになってしまい、無限再帰になる。

```java
record Record(String value){
    Record(){
        this(null);   // ← OK
    }
}
```
→ コンパイル成功。

つまり「何か具体的な意味のある値を渡さないといけない」わけではなく、**カノニカルコンストラクタ`Record(String value)`を実際に呼び出せる形（`String`型に合う引数を1つ）にする必要がある**、というだけ。渡す値の中身は`"sample"`でも`null`でも問われない。

## カノニカルコンストラクタのアクセス修飾子は、record本体以上でなければならない

```java
public record Data(String value) {
    Data {
        // publicなし
    }
}
```
```
エラー: レコードDataに無効な標準コンストラクタがあります
  ((public)より強いアクセス権限を割り当てようとしました)
```

`public record`なら、カノニカルコンストラクタも`public`にする必要がある（それより弱いとエラー）。逆に`record`（package-private）のままなら、コンストラクタもpackage-privateでよい（詳細は[[暗黙]]参照）。

## 追加のコンストラクタ（カノニカルの反対）

**カノニカルの反対＝「追加のコンストラクタ」**。ヘッダーと違う引数リストを持つコンストラクタのこと。

| | 引数リスト |
|---|---|
| カノニカルコンストラクタ | ヘッダーと**同じ**（`record Data(String value, int value2)`なら`(String value, int value2)`） |
| 追加のコンストラクタ | ヘッダーと**違う**（例：`(int value2)`、`()`など） |

「暗黙で作られるか・自分で書くか」は関係なく、**引数リストがヘッダーと一致しているかどうか**だけがカノニカルかどうかの判定基準（自分で明示的に書いても、ヘッダーと同じ引数リストならそれは依然としてカノニカル）。

### 追加のコンストラクタの引数は、コンポーネントと無関係な形で自由に作れる

```java
record Data(String value, int value2) {
    public Data(){            // 引数0個。コンポーネントの数・型とは無関係でOK
        this("S", 1);         // 最初の文で必ずthis(...)してカノニカルに委譲
    }
}
```
→ コンパイル成功（検証済み）。

recordが強制しているのは「**フィールドへの代入経路は必ずカノニカル1箇所に一本化する**」という点だけ。追加のコンストラクタ自体の引数の数や型は、普通のクラスの“オーバーロードされたコンストラクタ”と同じ感覚で自由に設計できる。守るべき唯一のルールは「**最初の文で`this(...)`を呼び、最終的にカノニカルへ辿り着くこと**」（詳細は上記「追加のコンストラクタは、必ず`this(...)`でカノニカルに委譲しなければならない」参照）。

### 追加のコンストラクタの引数を増やしても、`this(...)`には委譲先の引数リストを丸ごと渡す必要がある

追加のコンストラクタ自体の引数は自由に増やせるが、`this(...)`で委譲する側は「一部だけ渡して残りは省略」ということができない。委譲先のコンストラクタ（ここではカノニカル）の引数リストと**個数・型が一致する形**で渡す必要がある。

```java
record Data(String value, int value2) {
    public Data(String value, int value2, int value3) {
        this(value);   // ← valueだけ渡して省略しようとした
    }
}
```
```
エラー: Dataに適切なコンストラクタが見つかりません(String)
    コンストラクタ Data.Data(String,int,int)は使用できません...
    コンストラクタ Data.Data(String,int)は使用できません...
```

正しくは、カノニカルが要求する引数（`String, int`の2つ）をきちんと全部揃えて渡す。

```java
public Data(String value, int value2, int value3) {
    this(value, value2 + value3);   // ← 2つともきちんと渡す → OK
}
```

「追加のコンストラクタの引数の形は自由」だが、「`this(...)`で渡す中身は、呼び出し先のコンストラクタの引数リストにきっちり合わせる」という、ごく普通のオーバーロード解決のルールがそのまま適用されているだけ（record特有の特別ルールではない）。

## まとめ

- カノニカルコンストラクタ＝ヘッダーと同じ引数リストのコンストラクタ。書かなければ自動生成される。
- 追加のコンストラクタは、必ず`this(...)`でカノニカルに委譲するのが第一文でなければならない。
- `this(...)`に渡す引数は、カノニカルの引数型に合ってさえいればよい（値の中身は自由、`null`可）。
- `record`が`public`なら、カノニカルコンストラクタも`public`必須。
