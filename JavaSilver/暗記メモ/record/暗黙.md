# recordの特徴

## recordに「暗黙で」付くもの・付かないもの

| | 暗黙で付くか |
|---|---|
| `final`（継承不可） | ✅ 付く（書いても書かなくても継承不可、詳細は下記） |
| `extends java.lang.Record` | ✅ 付く（自分で`extends`を書くことは構文上できない） |
| `public`（アクセス修飾子） | ❌ 付かない（**普通の`class`と同じ**。修飾子を書かなければpackage-privateがデフォルト） |

```java
record Record(String value) {
    Record(String value) {   // publicなしでもOK
        this.value = value;
    }
}
```
→ コンパイル成功（検証済み）。もし`public`が暗黙で付くなら、レコード本体とコンストラクタのアクセスレベルが食い違ってエラーになるはずだが、ならない。これは「recordはpackage-privateのまま」という証拠。

一方で、レコード自体を`public record`と書いた場合は、**カノニカル（標準）コンストラクタもそれと同じ`public`にしなければならない**というルールがある（詳細は[[../カノニカルコンストラクタ/カノニカルコンストラクタのアクセス修飾子]]、なければ後述）。

```java
public record Data(String value) {
    Data {
        // publicなし
    }
}
```
```
エラー: レコードDataに無効な標準コンストラクタがあります
  ((public)より強いアクセス権限を割り当てようとしました)
```

**まとめ：「recordは暗黙でpublicになる」は誤り。ただし`public record`と書いたなら、カノニカルコンストラクタのアクセス修飾子はそれと釣り合わせる（＝`public`にする）必要がある、というのが正確なルール。**

## recordにはsealed/non-sealedが書けない（構文エラー）

`record`には`sealed`も`non-sealed`もそもそも書けません（構文エラー）。`record`は常に暗黙で`final`なので、sealed階層の一員として扱うための追加修飾子自体が不要かつ書けないのです。

```java
sealed interface Foo permits Product {
    void methodZ();
}
non-sealed record Product(int id) implements Foo {   // ← 構文エラー
    public void methodZ(){}
}
```
```
エラー: class, interface, enumまたはrecordがありません
```

選択肢Gの例（`non-sealed record`）自体がコンパイルエラーを起こす無効な例なので、この記述は誤りです。

## この問題最大のポイント

`class`が継承階層で使う`final`/`sealed`/`non-sealed`という3択は、`record`には一切適用されません（`record`は常に`final`固定で、それ以外の修飾子を付ける余地が構文上そもそも存在しない）。「レコードだからsealedにするなら特別な書き方が必要」という発想自体が罠で、正しくは「レコードには最初から`sealed`系の修飾子を書く必要も書く余地もない」という結論です。

`sealed`インターフェースを実装するレコードは、修飾子なし（デフォルト）か`final`（暗黙のものを明示するだけ）のどちらかしか書けません。
