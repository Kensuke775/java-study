# interfaceのオーバーライド（default/abstractの衝突）

※ファイル名は「オーバーロード」ですが、中身は「オーバーライド」（同じシグネチャのメソッドの再定義）に関する内容です。

## 基本ルール

無関係な2つのインターフェースが同じシグネチャのメソッドを持っていて、その両方を実装するクラスがどちらのメソッドをどう扱うか自動判断できない場合、Javaは**必ず実装クラス側での明示的なオーバーライドを要求**する。「片方がabstractだから、もう片方のdefaultが自動採用される」ということは一切ない。

## パターン1：default × default（衝突）

```java
interface X {
    double POINT_RATE = 0.05;
    default Number calculate(int price) {
        return (int)(price * POINT_RATE);
    }
}
interface Y {
    double TAX_RATE = 0.1;
    default Number calculate(int price) {
        return (int)(price * TAX_RATE);
    }
}
class One implements X, Y {}   // ← ここでコンパイルエラー
```

```
エラー: タイプXとYは互換性がありません。
クラス Oneは型XとYからcalculate(int)の関連しないデフォルトを継承します
```

`X`と`Y`はどちらも`calculate(int)`の**実装（default）を持っている**が、無関係なインターフェース同士なのでどちらを使うべきかコンパイラは判断できない → エラー。

## パターン2：default × abstract（実装なし側があっても免除されない）

```java
interface X {
    default Number calculate(int price) { return (int)(price * 0.05); }
}
interface Y {
    Number calculate(int price);   // 本体なし（abstract）
}
class One implements X, Y {}   // ← これもコンパイルエラー
```

```
エラー: Oneはabstractでなく、Y内のabstractメソッドcalculate(int)をオーバーライドしません
```

「`Y`は実装がないんだから、`X`のdefaultで自動的に埋めてくれるのでは？」と思いがちだが、**そうはならない**。エラーの種類はパターン1（`関連しないデフォルトを継承`）とは異なり、単に「未実装のabstractメソッドが残っている」という通常の実装漏れ扱いになる。結論はどちらも同じで、**実装クラス側での明示的なオーバーライドが必須**。

`abstract class`にしても、この診断は免除されない。

```java
abstract class One implements X, Y {}   // これもエラーのまま
```

## 解決方法

### 方法1：実装クラスでオーバーライドし、`X.super`で明示的に呼び分ける

```java
class One implements X, Y {
    public Number calculate(int price) {
        return X.super.calculate(price);   // Xのdefault実装を明示的に使う
    }
}
```

- `インターフェース名.super.メソッド名()` という構文は、**そのクラス（または呼び出し元インターフェース）が対象のインターフェースを直接implements/extendsしている場合にのみ**使える
- 例：`Y`が`X`を継承していない状態で、`Y`の中や`Y`を継承していない別クラスから`X.super`を書くとエラー（`Xは内部クラスを囲みません`）

### 方法2：戻り値の型を変えてオーバーライド（共変戻り値）

```java
class One implements X, Y {
    public Integer calculate(int price) {   // NumberのサブタイプIntegerでもOK
        return price - 100;
    }
}
```

オーバーライド時の戻り値は「元の型と同じ、またはそのサブタイプ」であればよい（共変戻り値）。`Integer`は`Number`のサブクラスなので合法。

### 方法3：一方のインターフェースがもう一方を継承する関係にする

```java
interface Y extends X {
    default Number calculate(int price) { return (int)(price * 0.1); }
}
class One implements Y {}   // Xを間接的に実装。Yのdefaultが自動的に優先される
```

`Y extends X`にすると、`Y`が`X`より特化した型になるため、**継承の優先順位ルールにより`Y`のdefaultが自動的に採用**され、曖昧さが解消される（実装クラス側でのオーバーライドは不要になる）。

## まとめ表

| ケース | 実装クラスでの対応 |
|---|---|
| default × default（無関係なインターフェース同士） | 必ずオーバーライドが必要（`X.super`で呼び分け可） |
| default × abstract（無関係なインターフェース同士） | 同じく必ずオーバーライドが必要（`abstract`クラスにしても免除されない） |
| 継承関係あり（`Y extends X`） | より特化した側のdefaultが自動採用され、オーバーライド不要 |
