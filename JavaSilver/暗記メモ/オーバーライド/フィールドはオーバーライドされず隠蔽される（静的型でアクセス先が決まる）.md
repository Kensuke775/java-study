# フィールドはオーバーライドされない。「隠蔽（シャドーイング）」され、静的型でアクセス先が決まる

## 検証コード：BとCの両方にvalueがある場合

```java
interface A {
    default void sample() { System.out.println("A"); }
}
abstract sealed class B implements A permits C {
    int value;
    public abstract void sample();
}
final class C extends B {
    int value;   // Bとは別の、独立したフィールド
    public void sample() {
        System.out.println("C");
        value += 100;   // ここのvalueはCの自分のフィールドを指す
    }
}

B c = new C();
c.sample();
System.out.println(c.value);              // → 0
System.out.println(((C) c).value);        // → 100
```
→ 検証済み。

## 検証コード：Cがvalueを持たない場合

```java
final class C extends B {
    // valueを持たない（Bのものをそのまま使う）
    public void sample() {
        System.out.println("C");
        value += 100;   // Bから継承したvalueを指す
    }
}

B c = new C();
c.sample();
System.out.println(c.value);   // → 100
```
→ 検証済み。`C`が独自の`value`を持たなければ、`B`の`value`をそのまま使うので、`B`型経由でも同じ値が見える。

## なぜこうなるのか

**フィールドは動的束縛（ポリモーフィズム）の対象になりません。** メソッドの「オーバーライド」とは全く別の仕組みで、名前が同じフィールドがサブクラスにもあると、それは上書きではなく**隠蔽（シャドーイング）**になる＝**2つの独立したフィールドが共存する**。

- `C`が独自の`value`を持つ場合：`C`と`B`は名前が同じでも完全に別々の2つのフィールドとして共存する。`C.sample()`内の裸の`value`は、**一番近いスコープにある`C`自身のフィールド**を指す（[[コンストラクタは代入必須ではない・裸の変数名は一番近いスコープ（問題18）]]と同じ「一番近いスコープ」のルール）。一方`c.value`は、`c`の**宣言型（静的型）である`B`のフィールド**にアクセスするため、`C`側でいくら加算しても`B`側のフィールド（`0`のまま）しか見えない。フィールドは**参照の静的型で直接アクセス先が決まり**、動的型を見て中身が切り替わることが無い。
- `C`が独自の`value`を持たない場合：`C`にはフィールドが存在しないので、`C.sample()`内の`value`は継承した`B`の`value`をそのまま指す。フィールドは1つしか無いので、`B`型経由で見ても同じものが見える。

## まとめ

| ケース | `c.value`（`B`型変数経由） |
|---|---|
| `B`と`C`の両方が`int value;`を持つ（隠蔽） | 変化しない（`B`側のまま） |
| `C`が`value`を持たず、`B`のものをそのまま使う | 変化する（同じフィールドを共有） |

- フィールドはメソッドと違い、**参照の静的型で直接アクセス先が決まる**（動的型を見て切り替わらない）
- サブクラスが同名のフィールドを宣言すると、それは「上書き」ではなく「隠蔽」＝別々の2つのフィールドが生まれる

## `super.フィールド`は「直近の1段階」しか見ない（問題41：3段階継承の例）

```java
class A {
    int num = 10;
    public double getValue() { return 0.0; }
}
class B extends A {
    @Override
    public double getValue() { return 1.0; }
}
class C extends B {
    @Override
    public double getValue() {
        System.out.println(super.num);   // Bはnumを持たない → 10
        return super.getValue();
    }
}
```
→ `10`が出力される。検証済み。

```java
class B extends A {
    int num = 20;   // Bが独自のnumを持つ（隠蔽）
    @Override
    public double getValue() { return 1.0; }
}
// Cのsuper.numは？
```
→ `20`が出力される。検証済み。

### 解釈

`C extends B extends A`という3段階の継承があっても、`C`から見た`super`は常に**直近の`B`だけ**を指す。`A`まで飛び越えてアクセスすることはできない。

- `B`が独自の`num`を持たない場合：`B`は`A`から`num`を**継承**しているだけなので、「`B`が持っているnum」＝実質`A`のnum。結果的に`A`の値（`10`）が見えるが、これは`B`を素通りして直接`A`にアクセスしたのではなく、あくまで`B`経由
- `B`が独自の`num`を持つ場合：`B`自身のフィールドが優先され、`A`の`num`は隠蔽されて見えなくなる（`20`が見える）

### interfaceの`型名.super.メソッド名()`との共通原則

[[インターフェース名.super.メソッド名()（問題6）]]で見た「`A.super.sample()`は`A`が直接の実装対象でないと使えない」というルールも、根っこは同じ「**`super`（または`型名.super`）は自分の直接の1段階上しか見ない**」という原則の別の現れ方。

| | 直近の1段階を素通しで見る（OK） | 間にある層を飛び越えて名指しする（NG） |
|---|---|---|
| フィールド | `super.num`（`B`が持たないので`A`のものが見える） | （このような明示的な飛び越し構文は無い） |
| interfaceのdefault | `B.super.sample()`（`B`は直接implementsしているのでOK） | `A.super.sample()`（`A`は間接関係なのでNG） |
