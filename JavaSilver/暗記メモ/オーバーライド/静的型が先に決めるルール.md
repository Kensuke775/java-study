# 静的型が先に決めるルール（呼べるかどうかは実体ではなく参照の型で決まる）

## 「参照」とは何か

```java
A a = new B();
```

- `new B()` → メモリ上に実際に作られる**実体**（`B`のインスタンス）
- `a` → その実体を指し示す**参照変数**。ただし`a`という変数自体の**型は`A`**（これを「静的型」と呼ぶ）

```
a（静的型:A） ---参照---> 実体:Bのインスタンス
```

「参照」とは、変数の中に実体そのものが入っているのではなく、実体の場所を指す“矢印”が入っている、という仕組みのこと。

## 核心：メソッドが「呼べるかどうか」は、実体ではなく参照の型（静的型）だけで決まる

```java
class A {
    public void hello() { System.out.println("hello"); }
}
class B extends A {
    public void bye() { System.out.println("bye"); }   // Bだけの新規メソッド
}

A a = new B();
a.bye();   // ← コンパイルエラー
```
```
エラー: シンボルを見つけられません
メソッド bye()、場所: タイプAの変数 a
```

コンパイラが「このメソッド呼べる？」を判定する時に見ているのは、**「矢印の先に何があるか（実体＝B）」ではなく「矢印そのものの型（aの型＝A）」**。`bye()`は`A`のクラス定義に存在しないので、実体が`B`であっても、そもそも呼び出し候補にすら入れない。

## オーバーライドされたメソッドは「大体呼べる」と感じる理由

普段よく見るパターンは「元々親クラスにも存在するメソッドを、子クラスで上書き（オーバーライド）している」場合。この場合は次の**2段階構造**で処理が進む。

1. **静的型（`A`）にそのメソッド名が存在するか**をコンパイル時にチェック → `hello()`は`A`にも存在するのでOK（土俵に上がれる）
2. 土俵に上がれたら、**実際にどちらの中身（AのhelloかBのhello）が動くかは実体（B）で決まる**（動的ディスパッチ）

```java
A a = new B();
a.hello();   // OK。呼べる（静的型Aにhelloがある）→ 実体がBならBのhello()が動く
```

「オーバーライドしてれば大体呼べる」と感じるのは、この1段階目（静的型チェック）を素通りできるケースばかり見ているから。今回の`bye()`のように**子クラスだけの完全に新規のメソッド**は、1段階目（静的型に存在するかどうか）で早々に弾かれる、という違い。

## まとめ

| | 判定基準 |
|---|---|
| ①「そのメソッドを呼び出せるか」（コンパイル時） | **参照の静的型**（`a`の型＝`A`）だけで決まる |
| ②「呼んだ時、実際にどちらの中身が動くか」（実行時） | **実体の型**（`new`した方＝`B`）で決まる（動的ディスパッチ） |

①をクリアしないと②の話にすら進めない、という順序が重要。「実体がBだから、Bのメソッドは何でも呼べるはず」は誤りで、正しくは「呼び出せるメソッドの候補は、あくまで参照の静的型が持つメソッドの中からしか選ばれない」。

## インターフェース経由でも同じルール（問題13・14）

```java
interface Worker { void work(); }
class Employee implements Worker {
    public void work() { System.out.println("work"); }
    public void report() { System.out.println("report"); }
}
class Engineer extends Employee {
    public void create() { System.out.println("create future"); }
}
```

```java
Worker a = new Engineer();
Employee b = new Engineer();
Engineer c = new Engineer();

a.create();   // ← コンパイルエラー：Workerはcreate()を知らない
a.work();     // ← OK：Workerがwork()を契約として持っている
b.work();     // ← OK：Employeeにwork()がある
c.report();   // ← OK：Engineerはreport()をEmployeeから継承している
```
→ すべて検証済み（`a.create()`のみ「シンボルを見つけられません」でコンパイルエラー）。

実体（`new`されたインスタンス）は3つとも同じ`Engineer`だが、`a`・`b`・`c`それぞれの**宣言型（静的型）**が違うため、呼べるメソッドの範囲が変わる。`Worker`型の`a`は`Worker`が知っているメソッド（`work()`）しか呼べず、`Engineer`が独自に持つ`create()`は`Worker`にも`Employee`にも存在しないので呼べない。

## オーバーライドしていなくても動的束縛のプロセス自体は同じように働く

`Engineer`は`work()`をオーバーライドしていないが、それでも`a.work()`は**動的束縛（動的ディスパッチ）を経て**呼ばれている。「オーバーライドされていないから動的束縛が働かない」わけではない。

```java
class EngineerOverride extends Employee {
    @Override
    public void work() {
        System.out.println("engineer's own work");
    }
}

Worker a = new EngineerOverride();
a.work();   // → "engineer's own work"
```
→ 検証済み。オーバーライドしている場合は`EngineerOverride`自身の実装が呼ばれる。

- **オーバーライドしていない場合**：動的型（`Engineer`）自身には実装が無いので、継承チェーンを1段上に辿って`Employee.work()`が見つかり、それが呼ばれる → 結果的に`"work"`
- **オーバーライドしている場合**：動的型（`EngineerOverride`）自身の実装がそのまま見つかる → `"engineer's own work"`

どちらのケースも「動的型から継承チェーンを辿って一番近い実装を探す」という同じ探索プロセスが働いている。オーバーライドの有無は、その探索が**どの階層で実装を見つけるか**を変えるだけで、探索プロセス自体の有無を左右しない。
