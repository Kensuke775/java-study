# 静的型が先に決めるルール（呼べるかどうかは実体ではなく参照の型で決まる）

## 「参照」とは何か

```java
A a = new B();
```

- `new B()` → メモリ上に実際に作られる**実体**（`B`のインスタンス）
- `a` → その実体を指し示す**参照変数**。ただし`a`という変数自体の**型は`A`**（これを「静的型」と呼ぶ）

```
a（静的型:A） ---参照---> 実体:Bのインスタンス
```

「参照」とは、変数の中に実体そのものが入っているのではなく、実体の場所を指す“矢印”が入っている、という仕組みのこと。

## 核心：メソッドが「呼べるかどうか」は、実体ではなく参照の型（静的型）だけで決まる

```java
class A {
    public void hello() { System.out.println("hello"); }
}
class B extends A {
    public void bye() { System.out.println("bye"); }   // Bだけの新規メソッド
}

A a = new B();
a.bye();   // ← コンパイルエラー
```
```
エラー: シンボルを見つけられません
メソッド bye()、場所: タイプAの変数 a
```

コンパイラが「このメソッド呼べる？」を判定する時に見ているのは、**「矢印の先に何があるか（実体＝B）」ではなく「矢印そのものの型（aの型＝A）」**。`bye()`は`A`のクラス定義に存在しないので、実体が`B`であっても、そもそも呼び出し候補にすら入れない。

## オーバーライドされたメソッドは「大体呼べる」と感じる理由

普段よく見るパターンは「元々親クラスにも存在するメソッドを、子クラスで上書き（オーバーライド）している」場合。この場合は次の**2段階構造**で処理が進む。

1. **静的型（`A`）にそのメソッド名が存在するか**をコンパイル時にチェック → `hello()`は`A`にも存在するのでOK（土俵に上がれる）
2. 土俵に上がれたら、**実際にどちらの中身（AのhelloかBのhello）が動くかは実体（B）で決まる**（動的ディスパッチ）

```java
A a = new B();
a.hello();   // OK。呼べる（静的型Aにhelloがある）→ 実体がBならBのhello()が動く
```

「オーバーライドしてれば大体呼べる」と感じるのは、この1段階目（静的型チェック）を素通りできるケースばかり見ているから。今回の`bye()`のように**子クラスだけの完全に新規のメソッド**は、1段階目（静的型に存在するかどうか）で早々に弾かれる、という違い。

## まとめ

| | 判定基準 |
|---|---|
| ①「そのメソッドを呼び出せるか」（コンパイル時） | **参照の静的型**（`a`の型＝`A`）だけで決まる |
| ②「呼んだ時、実際にどちらの中身が動くか」（実行時） | **実体の型**（`new`した方＝`B`）で決まる（動的ディスパッチ） |

①をクリアしないと②の話にすら進めない、という順序が重要。「実体がBだから、Bのメソッドは何でも呼べるはず」は誤りで、正しくは「呼び出せるメソッドの候補は、あくまで参照の静的型が持つメソッドの中からしか選ばれない」。
