# クラス自体の可視性とメンバーの可視性は別レイヤー（問題26）

## 検証コード

```java
// ex26パッケージ
public class Parent {
    int num = 10;   // 修飾子なし＝package-private
}

// otherパッケージ
package other;
import ex26.Parent;
public class Child extends Parent {
    public static void main(String[] args) {
        System.out.println(new Child().num);
    }
}
```
```
エラー: Parentのnumはpublicではありません。パッケージ外からはアクセスできません
```
→ 検証済み。

## `public class Sample`が保証しているのは「クラスという箱自体が見えること」だけ

```java
public class Sample {   // ← クラス自体は、どこからでも見える・importできる
    int num;            // ← このフィールド自体は修飾子なし＝package-private
}
```

`public class Sample`は「`Sample`という**箱（クラス）自体**は、どのパッケージからでも見える（`import`できる、変数の型に書ける、`new Sample()`できる）」ということしか保証していない。

**箱を開けた後、中の各フィールド・メソッドにアクセスできるかどうかは、それぞれが個別に持っているアクセス修飾子で決まる**。クラス自体が`public`でも、中のフィールドが無指定（package-private）なら、別パッケージからはそのフィールドだけ見えない。

## なぜ`extends`していても救われないのか

`Child extends Parent`のように継承していても関係ない。package-privateは「同じパッケージ内かどうか」だけで判定され、「サブクラスだから見える」という抜け道は無い（この点は`protected`と違う。`protected`なら別パッケージのサブクラスからでも見える）。

## イメージ

「建物（クラス）自体には誰でも入れる（`public`）が、建物の中の各部屋（フィールド・メソッド）には、部屋ごとに別々の鍵（アクセス修飾子）が掛かっている」という感覚が正確。「建物がpublicだから中身も全部publicのはず」という発想が誤り。

## まとめ

| レイヤー | 何が保証されるか |
|---|---|
| クラス自体の`public` | クラスという名前そのものが、どこからでも見える |
| メンバー（フィールド・メソッド）個別の修飾子 | そのメンバー個別に、どこまで見えるかが決まる（クラス自体の修飾子とは独立） |

2つのレイヤーは完全に独立していて、クラスが`public`かどうかは、中のメンバーの可視性には一切影響しない。
