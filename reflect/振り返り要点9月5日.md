  - `max()`, `min()`, `frequency()` → `Collection`**全般**(`List`でも`Set`でも使える、順序不要な操作)
  - `unmodifiableMap()`, `synchronizedMap()`など → `Map`**専用**メソッドも用意されている(`Map`は`Collection`を継承していないが、`Collections`クラス自体はMap用の静的メソッドも別途持っている)

### 9/5 (Silver 7章 例外処理 復習)

- `switch`式で`yield`はあるのに`default`が無いとコンパイルエラー(→代入式は値を必ず返す必要があり、非enum/非sealed型は網羅性を保証できないので`default`必須) yieldは収率という意味。
- `switch`文(矢印構文、代入なし)は`default`が無くてもOK(→式ではなく文だから)、矢印構文はフォールスルーしない
- `NumberFormatException`と`ClassCastException`の違い(→キャスト構文`(型)`で起きるのがCCE、parse系メソッドの文字列内容が原因で起きるのがNFE。継承階層上もCCEはRuntimeException直下、NFEはIllegalArgumentException経由)
- CCEと対比されるもう一つの例外は`ArrayStoreException`(→配列の共変性が原因、キャストを書いていないのに配列への代入時に実行時発覚)
- ループ内で`catch`されたら普通に次の周へ進む(例外は`catch`の中で解決済み扱い)
- `s.length()`(nullレシーバ)は`NullPointerException`、`Integer.parseInt(null)`(null引数)は`NumberFormatException`(→レシーバへのnullアクセスは機械的にNPE、引数として渡すだけならそのメソッドの実装次第)
- `finally`の中に`continue`/`break`/`return`があると、伝播中だった例外は完全に消える(finally自身の異常完了が優先され、握りつぶされる)
- `IndexOutOfBoundsException`単体(サブクラスでなく)が出るのは`List`系(`ArrayList.get`等)の添字操作のとき(配列・文字列には専用サブクラスがあるので単体では出ない)
- `ClassNotFoundException`が起きるのは`Class.forName("...")`のように文字列でクラス名を指定して動的ロードしようとして失敗したとき(`NoClassDefFoundError`との違いに注意)
- try-with-resourcesのリソース変数は実質的final必須。再代入が`try()`の前/中/後どこにあっても、コンパイルエラーは常に`try(fw1)`の行で報告される(IDEは再代入した行にも印を付けるが、javac自体はtry行のみ)
- try本体と`close()`の両方が例外を投げた場合、`catch`の型判定は主例外(try本体の例外)だけを見る。`close()`側の例外は`addSuppressed()`で付加されるだけで型マッチングには関与しない(→suppressed exception)

**振り返りチェック**

**switch式のyield/フォールスルーで気になったこと**

- コロン式(`case X:`)は、各caseに`yield`が無くてもフォールスルーして次のcaseへ進む。本当に文を実行してから流れ落ちる(単なるラベルのグループ化ではない)。必須なのは「実行される経路の最終的な行き着き先には必ず`yield`(か`throw`)がある」ことだけ(→どこにも無いと「switch式に結果式がありません」でコンパイルエラー)
- アロー式(`->`)+単一の式は`yield`を書けない・不要(式の値がそのまま結果。`case 1 -> yield "Low";`は構文エラー)
- アロー式+ブロック(`{ }`)は中で`yield`必須
- アロー式+`throw`は`yield`不要(`throw`自体が異常完了なので「値を返す」という要件が免除される)。ブロックの中で`throw`(他の処理をしてから投げる)、`->`の直後にそのまま`throw`、どちらの形もOK

**finallyの中でthrow/returnが起きた場合の優先順位で気になったこと**

- `catch`が`return`しようとしていても、`finally`の中で先に`throw`が実行されると、`finally`はその時点で異常完了する。`finally`内でそれより後ろに書いた`return`には一生たどり着けず、`catch`が返そうとしていた戻り値も丸ごと破棄される
- `try`本体で例外Aが発生し、`finally`でも例外Bが発生した場合(**try-with-resourcesではない、手動の**`try-catch-finally`)、**後から起きた例外Bだけが生き残り、先の例外Aは**`getSuppressed()`**にも**`getCause()`**にも残らず完全に消える**(`javac`/`java`で検証済み: suppressed count 0, cause null)
- これは try-with-resources の`close()`の挙動とは**逆**: close()側は「先に起きたtry本体の例外を守り、後から起きたclose側の例外は`addSuppressed()`で付加するだけで上書きしない」という設計。手動`finally`は逆に「後着き優先で先勝ちを保存しない」ので混同注意

**自作クラス名が**`Exception`**と衝突してハマったこと**

- 自分のファイル(パッケージ)の中に`public class Exception { ... }`のような、標準ライブラリと同名のクラスを定義すると、そのファイル内で`Exception`と書いたとき、コンパイラは`java.lang.Exception`ではなく**自作の方を優先して解決**してしまう
- 自作の`Exception`は`Throwable`を継承していないので、`catch (Exception e)`や`throws Exception`に使おうとすると「例外の型はThrowableのサブクラスでなければなりません」というコンパイルエラーになる
- `java.lang`パッケージ(`Exception`, `RuntimeException`, `Throwable`, `String`, `Object`, `Math`, `System`など)は全ファイルで自動importされているため、普段`import`を書かなくても使えている。ただしこの自動importは**名前解決の優先順位が一番低く**、同じファイル/パッケージ内の自作クラスに常に負ける
- 名前解決の優先順位: ①同じファイル内の型 → ②同じパッケージ内の型 → ③`import`した型 → ④`java.lang`(自動import)
- 対処: 自作クラスの名前を`Exception`以外に変える(推奨)、または使いたい方を`java.lang.Exception`のように完全修飾名で書く

**List/Arrays.asList の可変性**

- `Arrays.asList()`の中身は参照型か → 合ってる。可変長引数`T...`はプリミティブ不可なので、intリテラルを個別に渡すと自動でIntegerにオートボクシングされる。ただし配列そのものを渡すと、その配列自体が参照型として1要素扱いになる点に注意
- Listの可変性3段階の記憶違い → `new ArrayList<>()`(add/remove/set全部OK)と`Arrays.asList()`(add/removeはUnsupportedOperationException、setはOK)は合っていたが、`List.of()`の認識が誤り。`set()`で起きるのは`IndexOutOfBoundsException`ではなく`Arrays.asList()`のadd/removeと同じ`UnsupportedOperationException`(有効な範囲内のインデックスを指定しても、そもそも変更操作自体が許可されていないため)。整理の軸は「add/removeが可能か」「setが可能か」の2軸

**TreeSet + Comparableで疑問に思ったこと**

- `TreeSet`は`add()`時、要素が既存要素と`compareTo()`で「等しい(0)」と判定されると、`equals()`の結果に関わらず**重複として弾く**(=追加されない、`size()`が増えない)
- `compareTo()`を`this.name.compareTo(o.name)`(名前だけで比較)にすると、`("Bob",20)`と`("Bob",30)`は名前が同じなので比較結果が`0`になり、後から追加した方は弾かれて`size()`は`2`になる
- `compareTo()`を`this.age - o.age`(年齢だけで比較)に変えると、3人とも年齢が違うので誰も重複せず`size()`は`3`になり、年齢の昇順で並ぶ
- `record`(`Client`)自体は`equals()`/`hashCode()`を全フィールドで自動生成するが、`TreeSet`はその自動生成された`equals()`を一切見ておらず、あくまで`Comparable`(または渡された`Comparator`)の比較結果だけで重複判定している、という点がポイント
