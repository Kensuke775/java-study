# 公式サンプルC メモ

## 問題1：検証と妥当性確認（シラバス1.1.1）

**言葉の意味は「比べる相手」とセットで決まっている**

| 言葉 | 比べる相手 | 覚え方 |
|---|---|---|
| 検証 | **仕様化された要件**（文書・仕様） | 「**仕様書どおり**に作れたか」 |
| 妥当性確認 | **ユーザーやステークホルダーのニーズ・期待** | 「**ユーザーが本当に欲しかったもの**か」 |

- 妥当性確認は「人に対して」ではなく「**人のニーズや期待**に対して」

**問題1のひっかけ：言葉の入れ替え**

| 選択肢 | 書いてある組み合わせ | 正しく直すと |
|---|---|---|
| A | 文書化された要件 × **妥当性確認** | 文書化された要件 × **検証** |
| D | ユーザーの期待 × **検証** | ユーザーの期待 × **妥当性確認** |

- どちらも言葉を入れ替えれば正しい文になる（公式解説）
- 試験の手順：
  1. 「検証」か「妥当性確認」を見つける
  2. 相手が「文書・要件・仕様」か「ユーザー・期待・ニーズ」かを見る
  3. 組み合わせが逆なら、どんなに正しそうでも ×
- モンハンの例（理解用）：検証＝仕様書の「スタミナ0でダッシュ不可」どおり動くか。妥当性確認＝仕様どおりでも、プレイヤーが「スタミナの減りが早すぎて楽しくない」と感じないか

## 問題2：テストとデバッグ（シラバス1.1.2・1.2.3）

**つながり**

```
根本原因 → エラー → 欠陥 → 故障
（なぜミスしたか）（人のミス）（コードの間違い）（起きた結果）
```

| | 意味 | モンハンの例（理解用） |
|---|---|---|
| 根本原因 | エラーにつながる状況が発生する**根底の理由**（1.2.3） | 締め切りに追われていた／仕様の説明を受けていなかった |
| エラー | 人のミス。欠陥を生み出す | 開発者がスタミナ0の判定を書き忘れた |
| 欠陥 | コードやドキュメントの間違い | コードに `stamina > 0` のチェックがない |
| 故障 | 欠陥が実行されて起きた結果 | スタミナ0でもダッシュできてしまう |

- **エラー ≠ 根本原因**。根本原因は、エラーの**さらに手前**（なぜエラーが起きたか）
- 欠陥の**原因** ＝ 人間のエラー（問題2 D の公式解説）

**テストとデバッグの役割**

| 活動 | やること |
|---|---|
| テスト | 故障を引き起こす（動的テスト）、欠陥を直接見つける（静的テスト）＝欠陥が**ある**ことを明らかにする |
| デバッグ | 故障の再現 → 診断（根本原因を発見すること）→ 原因を修正すること。実際に取り除くのは**欠陥** |
| 根本原因分析 | 根本原因を特定する。取り除けば同様の故障や欠陥を防げる（1.2.3） |

- テストとデバッグは**別の活動**
- **故障は再現するもの、欠陥は直すもの**。「デバッグは故障を修正する」は ×（問題2 A）→「テストは故障を引き起こし、デバッグは**欠陥**を修正する」なら正しい
- 「欠陥の**原因**を見つける・修正する」は ×（問題2 D）。欠陥と欠陥の原因（エラー）は別物
- テストの目的（1.1.1）に**根本原因の特定は入っていない**。根本原因の特定はデバッグの一部で、テストとは別（問題1 C）
- 「テストは否定的な活動」は ×（問題2 B）。テストもデバッグも品質向上に貢献する肯定的な活動
