## 1章 テストの基礎

### テストとは

- テスト ＝ 欠陥を見つけ、品質を評価する**一連の活動**（実行するだけではない）
- **検証**：仕様どおりに作れているか
- **妥当性確認**：ユーザーのニーズを満たしているか
- **動的テスト**：ソフトを実行する ／ **静的テスト**：実行しない（レビュー・静的解析）



### テストとデバッグは別物

- テスト：故障を起こす・欠陥を見つける
- デバッグ：原因を見つけて直す（再現 → 診断 → 修正）
- 修正後に行うのが **確認テスト**（直ったか）と **リグレッションテスト**（他を壊していないか）



### テスト（QC）と品質保証（QA）は別物


|      | QC（品質コントロール） | QA（品質保証） |
| ---- | ------------ | -------- |
| 対象   | プロダクト        | プロセス     |
| 性質   | 是正的          | 予防的      |
| テストは | QCの一形式       | —        |




### エラー → 欠陥 → 故障

- **エラー（誤り）**：人間のミス
- **欠陥（バグ・フォールト）**：成果物に入り込んだ問題
- **故障**：欠陥が実行されて、期待と違う動きをすること
- **根本原因**：エラーが起きた根本の理由（根本原因分析で特定）
- 故障は環境条件（放射線など）でも起こる



### テストの7原則（頻出）

1. テストは欠陥があることは示せるが、**ないことは示せない**
2. **全数テストは不可能**（技法・優先順位付け・リスクで絞る）
3. **早期テスト**で時間とコストを節約（シフトレフト）
4. **欠陥の偏在**（少数のコンポーネントに集中 ＝ パレートの法則）
5. **テストの弱化**（同じテストを繰り返すと新しい欠陥が見つからなくなる）
6. **テストはコンテキスト次第**
7. **「欠陥ゼロ」の落とし穴**（バグがなくてもユーザーの役に立たなければ意味がない）



### テストプロセス（7つの活動）


| 活動            | 内容                         |
| ------------- | -------------------------- |
| テスト計画         | 目的とアプローチを決める               |
| モニタリングとコントロール | 進捗を計画と比べ、必要なら手を打つ          |
| テスト分析         | **何を**テストするか（テスト条件を決める）    |
| テスト設計         | **どのように**テストするか（テストケースを作る） |
| テスト実装         | テストデータ・手順・環境を準備する          |
| テスト実行         | 実行して期待結果と比べ、不正を報告する        |
| テスト完了         | テストウェアの保管、教訓の整理、完了レポート     |


- 各活動の成果物を **テストウェア** と呼ぶ
- テストベースとテストウェアをつなぐ **トレーサビリティ** が、カバレッジ評価や変更影響の判断に役立つ
- 役割は2つ：**テストマネジメントをする役割**（計画・モニタリング・完了）と **テストをする役割**（分析・設計・実装・実行）



### スキルと独立性

- テスト担当者は「悪い知らせの運び手」。欠陥は**建設的に伝える**（**確証バイアスに注意**）
- **チーム全体アプローチ**：全員が品質に責任を持つ（XP由来）
- **独立性の度合い**：作成者本人（なし）→ 同じチームの仲間 → チーム外・組織内 → 組織外（とても高い）
  - 利点：開発者と違う視点で欠陥を見つけられる
  - 欠点：孤立・対立、開発者が品質への責任感を失う、ボトルネック扱いされる

## 2章 SDLC全体を通してのテスト



### 開発モデルとテストの関係

- **シーケンシャル**（ウォーターフォール・V字）：初期はレビューや設計に参加し、動的テストは後半
- **イテレーティブ／インクリメンタル**：各イテレーションで静的・動的テストを実施。リグレッションテストが多くなる
- **アジャイル**：ドキュメントは軽め、自動化を重視、手動テストは経験ベース技法が中心



### よい実践例（どのモデルでも共通）

- すべての開発活動に、対応するテスト活動がある
- テストレベルごとに目的が違う（重複を避ける）
- テスト分析・設計は、対応する開発フェーズの間に始める
- ドラフトができたらすぐレビューに参加する



### テスト駆動の開発手法


| 手法   | 特徴                                |
| ---- | --------------------------------- |
| TDD  | テストを先に書く → コードを書く → リファクタリング      |
| ATDD | 受け入れ基準からテストを先に作る                  |
| BDD  | **Given/When/Then** の自然言語でふるまいを書く |




### DevOps とシフトレフト

- **DevOps**：開発と運用が協力する組織的アプローチ。CI/CDで速いフィードバック
  - 自動化が前提だが、**ユーザー視点の手動テストは依然必要**
- **シフトレフト**：テストをなるべく早い段階で行うこと（後半のテストを軽視するわけではない）
- **ふりかえり**：うまくいったこと・改善点を話し合い、テスト完了レポートに記録する



### 5つのテストレベル


| レベル              | 焦点               | 主な担当       |
| ---------------- | ---------------- | ---------- |
| コンポーネントテスト（ユニット） | 単体の部品            | 開発者        |
| コンポーネント統合テスト     | 部品間のインターフェース     | 開発者        |
| システムテスト          | システム全体の機能・非機能    | 独立したテストチーム |
| システム統合テスト        | 他システム・外部サービスとの接続 | テストチーム     |
| 受け入れテスト          | 妥当性確認・デプロイ準備     | ユーザー・ビジネス側 |


- 受け入れテストの種類：UAT、運用受け入れ、契約・規制による受け入れ、アルファ／ベータ



### 4つのテストタイプ


| タイプ         | 見るもの                                             |
| ----------- | ------------------------------------------------ |
| 機能テスト       | 「**何を**」するか                                      |
| 非機能テスト      | 「**どのくらいうまく**」動くか（性能・互換性・使用性・信頼性・セキュリティ・保守性・移植性） |
| ブラックボックステスト | 仕様に基づく                                           |
| ホワイトボックステスト | 内部構造（コード）に基づく                                    |


- テストタイプは **どのテストレベルでも** 使える



### 確認テストとリグレッションテスト

- **確認テスト**：欠陥が直ったかを確認する
- **リグレッションテスト**：変更で他に悪影響が出ていないかを確認する → **自動化の有力候補**
- まず **影響度分析** でリグレッションテストの範囲を決める



### メンテナンス（保守）テスト

- きっかけ：**改良**（機能拡張・修正・ホットフィックス）、**環境の更新・移行**、**廃棄**
- 範囲を決める要素：変更のリスク、既存システムの大きさ、変更の大きさ

## 3章 静的テスト



### 静的テストの基本

- ソフトを**実行せずに**評価する（人によるレビュー、ツールによる静的解析）
- 読めるものなら何でもレビューできる。静的解析には構造（コード・モデルなど）が必要
- 価値：早期に見つかる、動的テストで見つからない欠陥（到達不能コードなど）も見つかる、全体コストが下がる



### 静的テストと動的テストの違い


|       | 静的テスト          | 動的テスト              |
| ----- | -------------- | ------------------ |
| 見つけ方  | 欠陥を**直接**見つける  | 故障を起こし、分析して欠陥を特定する |
| 対象    | 実行できない成果物にも使える | 実行できるものだけ          |
| 測れる品質 | 保守性など          | 性能効率性など            |


静的テストで見つけやすい欠陥：要件の矛盾・曖昧さ、設計の欠陥、未定義の変数・到達不能コード、コーディング標準違反、インターフェース仕様の不一致、一部のセキュリティ脆弱性

### レビュープロセス（5つの活動）

1. **計画**：範囲・目的・終了基準を決める
2. **レビューの立ち上げ**：参加者と資料の準備を確認する
3. **個々人のレビュー**：各自が不正・推奨・質問を記録する
4. **共有と分析**：不正を議論し、対応を決める
5. **修正と報告**：欠陥レポートを作成し、結果を報告する



### レビューの役割


| 役割               | 責務                  |
| ---------------- | ------------------- |
| マネージャー           | 何をレビューするか決め、リソースを出す |
| 作成者              | 成果物を作り、直す           |
| モデレーター（ファシリテーター） | ミーティングを運営する         |
| 書記（記録係）          | 不正や決定事項を記録する        |
| レビューア            | レビューする              |
| レビューリーダー         | レビュー全体に責任を持つ        |




### レビュー種別（形式度：低 → 高）


| 種別        | 主導         | ポイント                                      |
| --------- | ---------- | ----------------------------------------- |
| 非形式的レビュー  | —          | プロセスも文書化も不要                               |
| ウォークスルー   | **作成者**    | 教育・合意形成など目的が多い。事前の個人レビューは任意               |
| テクニカルレビュー | **モデレーター** | 技術的な合意・判断                                 |
| インスペクション  | —          | **最も形式的**。不正を最大数見つける。**作成者はリーダーや書記になれない** |




### レビューの成功要因

- 明確な目的と測定可能な終了基準（**参加者の評価を目的にしない**）
- 対象を小さく分ける、準備時間を確保する、マネジメントが支援する、トレーニングする

## 4章 テスト分析と設計（最重要）



### 技法の3分類


| 分類       | 別名    | 基にするもの                  |
| -------- | ----- | ----------------------- |
| ブラックボックス | 仕様ベース | 仕様（実装が変わってもテストケースは使える）  |
| ホワイトボックス | 構造ベース | 内部構造（設計・実装の後でないと作れない）   |
| 経験ベース    | —     | テスト担当者の知識と経験（他の技法を補完する） |




### ブラックボックステスト技法

**同値分割法（EP）**

- 同じように処理される値をグループ（パーティション）に分け、**各パーティションから1つ**テストする
- 有効パーティションと無効パーティションの**両方**をカバーする
- カバレッジ ＝ 通したパーティション数 ÷ 全パーティション数
- パーティションが複数セットある場合の最小基準：**イーチチョイスカバレッジ**（組み合わせは考えない）

**境界値分析（BVA）**

- 順序のあるパーティションの**境界**をテストする
- **2値BVA**：境界値 ＋ 隣のパーティションの最も近い値（境界ごとに2つ）
- **3値BVA**：境界値 ＋ その両隣（境界ごとに3つ）→ 2値より厳密
  - 例：`x <= 10` を誤って `x == 10` と実装した場合、2値（10, 11）では見つからないが、3値の9で見つかる

**デシジョンテーブルテスト**

- 条件の組み合わせとアクションを表にする
- 表記：T（真）、F（偽）、`-`（無関係）、N/A（実行不可能）、X（アクションが起きる）
- カバレッジアイテム ＝ **実行可能な列**（ルール）
- 条件が増えると列は指数関数的に増える → 最小化やリスクベースで絞る

**状態遷移テスト**

- 遷移の書き方：「イベント［ガード条件］／アクション」
- 状態表は**無効な遷移も**明示する（空のセル）


| カバレッジ            | 対象            | 強さ                     |
| ---------------- | ------------- | ---------------------- |
| 全状態カバレッジ         | すべての状態        | 弱い                     |
| 有効遷移カバレッジ（0スイッチ） | すべての有効な遷移     | 最もよく使われる               |
| 全遷移カバレッジ         | 有効な遷移 ＋ 無効な遷移 | 最も強い（セーフティクリティカルの最低要件） |


- 無効な遷移は **1テストケースに1つだけ**（欠陥のマスキングを防ぐ）



### ホワイトボックステスト技法

- **ステートメントカバレッジ**：実行したステートメント数 ÷ 全ステートメント数
- **ブランチカバレッジ**：通したブランチ数 ÷ 全ブランチ数
- **ブランチ100% ならステートメント100%**（逆は成り立たない）
- 100%でも欠陥がすべて見つかるわけではない（例：ゼロ除算のようにデータに依存する欠陥）
- 弱点：**実装されていない要件（欠落）は見つけられない**



### 経験ベースのテスト技法


| 技法             | 内容                                                    |
| -------------- | ----------------------------------------------------- |
| エラー推測          | 過去の経験から起きそうなエラーを予測する。系統的にやるのが**フォールト攻撃**              |
| 探索的テスト         | 学びながら設計・実行・評価を同時に行う。**セッションベース**（時間枠＋テストチャーター）で体系化できる |
| チェックリストベースドテスト | チェックリストに沿ってテストする。欠陥分析に基づき定期的に更新する                     |




### コラボレーションベースのテストアプローチ

- ユーザーストーリーの **3つのC**：カード（Card）、会話（Conversation）、確認（Confirmation ＝ 受け入れ基準）
- よいユーザーストーリーの条件 **INVEST**：独立、交渉可能、価値がある、見積り可能、小さい、テスト可能
- 受け入れ基準の書き方：**シナリオ指向**（Given/When/Then）と **ルール指向**（箇条書き・表）
- **ATDD**：実装前にテストケースを作る。順番は ポジティブ → ネガティブ → 非機能

## 5章 テスト活動のマネジメント



### テスト計画書

- 内容：テストの概要（スコープ・対象・制約）、前提、ステークホルダー、コミュニケーション、リスクレジスター、テストアプローチ、予算とスケジュール
- アジャイルでは **リリース計画** と **イテレーション計画** の2種類があり、テスト担当者も参加する



### 開始基準と終了基準

- **開始基準**：始めるための前提条件（リソース、テストウェア、初期品質など）
- **終了基準**：完了と言える条件（カバレッジ、未解決欠陥数など）
- 時間切れ・予算切れも、ステークホルダーがリスクを受け入れれば終了基準として認められる
- アジャイルでは：終了基準 ＝ **完了（Done）の定義**、開始基準 ＝ **準備完了（Ready）の定義**



### 見積り技法（計算問題が出る）


| 技法          | 種類       | 内容                                              |
| ----------- | -------- | ----------------------------------------------- |
| 比率に基づく見積り   | メトリクスベース | 過去の比率を使う。例：開発:テスト ＝ 3:2、開発600人日 → テスト400人日      |
| 外挿          | メトリクスベース | 現在のプロジェクトの実績から推定する。例：直近3イテレーションの平均              |
| ワイドバンドデルファイ | 専門家ベース   | 各自が見積り → 議論 → 再見積りを合意まで繰り返す。**プランニングポーカー**はその一種 |
| 三点見積り       | 専門家ベース   | **E = (a + 4m + b) / 6**、**SD = (b − a) / 6**   |


三点見積りの例：a=6、m=9、b=18 → E = (6 + 36 + 18) / 6 = 10、SD = (18 − 6) / 6 = 2 → **10±2人時**

### テストケースの優先順位付け

- **リスクに基づく**：重要なリスクをカバーするものから
- **カバレッジベース**：カバレッジが最も高いものから（追加カバレッジが最大のものを次に選ぶ方法もある）
- **要件に基づく**：重要な要件に関わるものから
- ただし**依存関係があれば、優先度が低くても先に実行**する



### テストピラミッドとテストの四象限

- **テストピラミッド**：下（ユニット）ほど小さく速く数が多い、上（E2E）ほど遅く数が少ない
- **テストの四象限**


| 象限  | 向き     | 目的       | 例                              |
| --- | ------ | -------- | ------------------------------ |
| 第一  | テクノロジー | チームを支援   | コンポーネントテスト、コンポーネント統合テスト（自動化）   |
| 第二  | ビジネス   | チームを支援   | 機能テスト、ユーザーストーリーテスト、APIテスト      |
| 第三  | ビジネス   | プロダクトを批評 | 探索的テスト、使用性テスト、UAT（手動が多い）       |
| 第四  | テクノロジー | プロダクトを批評 | スモークテスト、非機能テスト（使用性を除く）（自動化が多い） |




### リスクマネジメント

- リスクレベル ＝ **リスクの可能性 × リスクの影響**
- **プロジェクトリスク**：プロジェクトの管理に関わる（納期遅れ、スキル不足、ツール不備、サプライヤーの問題）
- **プロダクトリスク**：プロダクトの品質に関わる（機能の誤り、応答が遅い、セキュリティ脆弱性）
- プロダクトリスク分析 ＝ **リスク識別** ＋ **リスクアセスメント**
- プロダクトリスクコントロール ＝ **リスク軽減** ＋ **リスクモニタリング**
- リスクへの対応：テストによる軽減、受け入れ、移転、コンティンジェンシー計画
- リスクに基づいてテストを選び優先順位を付けるのが **リスクベースドテスト**



### モニタリング・コントロール・完了

- **モニタリング**：情報を集めて進捗を測る ／ **コントロール**：その情報を使って手を打つ
- **テスト進捗レポート**：定期的に作る（期間、進捗、阻害要因、メトリクス、リスク、次の予定）
- **テスト完了レポート**：完了時に作る（評価、計画からの逸脱、未解決のリスクと欠陥、教訓）



### 構成管理

- テストウェアを構成アイテムとして識別・管理・追跡する
- 承認されたものは **ベースライン** になり、正式な変更管理でしか変えられない



### 欠陥マネジメント

- 報告された「不正」が本当の欠陥とは限らない（偽陽性、変更要求の場合もある）
- 欠陥レポートの主な項目：識別子、タイトル、日付・起票者、テスト対象と環境、再現手順、**期待結果と実際の結果**、**重要度**（影響の大きさ）、**優先度**（修正の急ぎ度）、状態

## 6章 テストツール



### ツールの種類

マネジメント、静的テスト、テスト設計・実装、テスト実行とカバレッジ、非機能テスト、DevOps、コラボレーション、仮想マシン・コンテナ、その他（表計算ソフトもテストツールになる）

### テスト自動化の利点とリスク


| 利点                 | リスク                           |
| ------------------ | ----------------------------- |
| 反復作業の削減・時間の節約      | ツールへの非現実的な期待                  |
| 一貫性・再現性が上がる        | 導入・保守の工数見積りが甘い                |
| 客観的な評価（カバレッジなど）    | 手動の方が適切な場面でツールを使う             |
| テスト情報にアクセスしやすい     | ツールに頼りすぎて批判的思考を失う             |
| 実行時間が短く、フィードバックが速い | ベンダーの廃業・サポート不足                |
| 新しいテストを設計する時間が増える  | OSSの放置、プラットフォーム非互換、規制に合わないツール |
