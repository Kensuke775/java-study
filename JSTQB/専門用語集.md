## テストの活動・管理

| 用語 | 英語 | 意味 | 初出 |
| --- | --- | --- | --- |
| 品質ゲート（クオリティゲート） | quality gate | 次の工程に進めてよいかを判定する品質チェック。最後だけとは限らない | 黒本1-1 |
| モニタリング | monitoring | 進捗を計画と比べて**見張る**こと | 1.4.1 |
| コントロール | control | モニタリングで分かったずれに**手を打つ**こと | 1.4.1 |
| ブロック | blocked | テストケースを実行できない、または実行しても結果が分かっていて意味がない状態 | 1.4.1 |
| カバレッジ | coverage | テスト対象のうち、テストした割合（網羅率）。例：要件カバレッジ、コードカバレッジ | 1.4.1 |
| トレーサビリティ | traceability | 要件 ↔ テスト条件 ↔ テストケース ↔ 結果 ↔ 欠陥 の**つながりをたどれる**こと | 1.4.4 |
| IT ガバナンス | IT governance | 組織が IT を適切に管理・統制するためのルール。トレーサビリティで基準を満たせる | 1.4.4 |

| QC | Quality Control（品質管理） | **プロダクト**を確かめて欠陥を見つける。テストはここ | 1.2 |
| QM（QMS） | Quality Management (System)（品質マネジメント） | QA と QC を含む、品質に関する全体の管理 | 1.2 |
| 探索的テスト | exploratory testing | テストを設計しながら同時に実行していくやり方。仕様が不十分でも短時間で大事な動作を確かめられる | 黒本1章 |
| アドホックテスト | ad hoc testing | 事前の計画やテストケースなしに、思いつきで行うテスト | 黒本1章 |

| スクリプトテスト（記述式テスト） | scripted testing | 設計書からテストケースを作り、それに沿ってテストする。スクリプト＝脚本 | 黒本1-1 |

| モンキーテスト（ゴリラテスト） | monkey testing | 意図を考慮しない操作で、思わぬ欠陥を見つける | 黒本1-1 |
| カットオーバークライテリア | cut-over criteria | 本稼働判定の基準（稼働判定基準・リリース判定基準） | 黒本1-1 |
| 欠陥（フォールト、バグ） | defect / fault / bug | 人間のエラー（誤り）が作業成果物に入ったもの。実行すると故障を起こすことがある | 黒本1-2 |
| 設計バグ | design bug | 設計フェーズで生じる欠陥。設計書の記載漏れも欠陥 | 黒本1-2 |
| 根本原因分析 | root cause analysis | 故障 → 欠陥 → 原因 と遡り、欠陥を埋め込んだ最初の行為（根本原因）を探す。なぜなぜ分析など。目的はプロセス改善 | 黒本1-2 |
| 悪魔の証明 | — | "ない" ことの証明は困難（原則1） | 黒本1-3 |
| 殺虫剤のパラドックス | pesticide paradox | テストの弱化の別名（原則5） | 黒本1-3 |
| コンテキスト | context | 背景や状況。状況次第でテストの方法が変わる（原則6） | 黒本1-3 |
| 不正 | anomaly | 実行結果と期待結果の差異。分析して原因を特定する（偽陽性のこともある） | 黒本1-4 |
| プロダクトバックログ | product backlog | 優先的に行うべき作業のリスト。テストでは未解決の欠陥などの課題 | 黒本1-4 |
| 確証バイアス | confirmation bias | もっている信念に合わない情報を受け入れがたくする心理。開発者の「コードは正しい」など | 黒本1-5 |
| アクションアイテム | action item | 今後のプロジェクトやイテレーションで実行すべき項目。テスト完了レポートに含める | 黒本1-4 |
| 認知バイアス | cognitive bias | 思い込みで正しく判断できなくなることの総称。後知恵バイアス、正常性バイアス、確証バイアスなど | 黒本1-5 |
| マインドセット | mindset | あるグループに共通する物事の捉え方・思考の方向性 | 黒本1-5 |
| チームダイナミクス | team dynamics | チームの相互作用の活性化。チーム全体アプローチの目標 | 黒本1-5 |
| セーフティクリティカル | safety-critical | 絶対にエラーが起こってはならないシステム | 黒本1-5 |
| オンサイト／オフサイト | on-site / off-site | 組織外テスト担当者の作業場所。社内（インハウス）／社外（アウトソーシング） | 黒本1-5 |
| メトリクス | metrics | 活動を定量化した指標（テストの進捗度、欠陥検出数、不良率など）。テストモニタリングで使う | 黒本1-4 |
| フィーチャー／フィーチャーセット | feature / feature set | ユーザーから見た機能や特徴／同じ類いのフィーチャーのセット | 黒本1-4 |
| 冗長なステートメント | redundant statement | 無駄に長いコードや文章。欠陥の種類の1つ | 黒本1-4 |
| 偽陽性 | false positive | 欠陥がないのに不合格になる（誤検出） | 1.2 |
| 偽陰性 | false negative | 欠陥があるのに合格になる（見逃し） | 1.2 |

| 用語 | 英語 | 意味 | 初出 |
| --- | --- | --- | --- |

## テストレベル・テストタイプ

| 用語 | 英語 | 意味 | 初出 |
| --- | --- | --- | --- |
| ユニットテスト／モジュールテスト | unit / module testing | コンポーネントテストの別名（日本では単体テスト） | 黒本1-1 |
| 境界値分析 | boundary value analysis | 境界の両側の値（例：5,000円と4,999円）を試すテスト技法 | 黒本1-3 |
| バリデーションチェック | validation check | 入力された値が妥当かどうかを判定すること。必須チェックはその一種 | 黒本1-3 |
| フェールセーフ | fail-safe | 異常が発生した場合に安全側に動作する仕組み | 黒本1-3 |
| 負荷テスト | load testing | アクセス急増などの負荷をかけたときの動作を確かめるテスト | 黒本1-3 |
| スタブ | stub | 呼ばれる側の代役（テスト対象が呼び出す相手の偽物） | 2.2.1 |
| ドライバー | driver | 呼ぶ側の代役（テスト対象を呼び出す仮のプログラム） | 2.2.1 |
| モック | mock | 呼び出され方まで確認できる代役 | 2.2.1 |
| ビッグバン統合 | big-bang integration | 全部を一度に統合する。欠陥の場所が特定しにくい | 2.2.1 |
| エンドツーエンド | end-to-end | 入口から出口まで、通しで動きを確認すること | 2.2.1 |
| ステージング環境 | staging environment | 本番にできるだけ近づけたテスト用の環境 | 2.2.1 |
| UAT | User Acceptance Testing | ユーザー受け入れテスト | 2.2.1 |
| アルファテスト／ベータテスト | alpha / beta testing | 市場に出す前に、社内（アルファ）や一部のユーザー（ベータ）に使ってもらう | 2.2.1 |
| ブラックボックステスト | black-box testing | 仕様に基づき、外から見た動作をテストする | 2.2.2 |
| ホワイトボックステスト | white-box testing | 内部構造（コードなど）に基づいてテストする | 2.2.2 |
| リグレッションテスト | regression testing | 変更で、ほかの部分に悪影響（退行）が出ていないか確かめる | 2.2.3 |
| デグレーション（デグレ） | degradation | 「悪くなる」。通常はリグレッションと同じ意味で使う | 黒本1-4 |
| ホットフィックス | hotfix | 本番の欠陥を直すための、計画外の緊急リリース | 2.3 |
| テストプロセス | test process | テストを進めるための活動のまとまり（計画→モニタリングとコントロール→分析→設計→実装→実行→完了） | 1.4.1 |
