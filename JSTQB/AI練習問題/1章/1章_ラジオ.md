## 1.1 テストとは何か？

### 問題1

米国の商品を日本で販売するアプリで、仕様書には「ドル価格に為替レートを掛けた金額を販売額とする」と書かれている。テストの結果、2ドルの商品が仕様どおり289.28円と表示された。テスト担当者が「日本円に小数点以下の硬貨はないので、この仕様のままでよいのか」と関係者に確認した。この確認にあたるものはどれか。

- a. 検証
- b. デバッグ
- c. 妥当性確認
- d. 確認テスト

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：c**

- **a**：誤り。仕様どおりかを確かめるのが検証。289.28円は仕様どおりなので検証はOKだが、ここでは仕様そのものを疑っている。
- **b**：誤り。デバッグは故障の原因を見つけて直す開発の活動。仕様を関係者に確認することではない。
- **c**：正解。仕様そのもの（期待結果）が正しいかを確認するのが妥当性確認。0.28円の硬貨はないので、この仕様のままでよいかを確かめている。
- **d**：誤り。確認テストは、欠陥を直した後に故障が解決したかを確かめるテスト。


### 問題2

次のうち、デバッグの活動にあたるものはどれか。

- a. 特定の入力で異常終了することを、テストケースの実行で見つける
- b. 異常終了の原因をデバッガーで突き止め、該当するコードを修正する
- c. 修正後に、異常終了が起きなくなったことを最初のテスト担当者が確かめる
- d. テストを始める前に、テストの目的と終了基準を決める

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：b**

- **a**：誤り。テストケースを実行して故障を見つけるのはテスト。
- **b**：正解。故障の原因をデバッガーで突き止め、コードを修正するのがデバッグ。
- **c**：誤り。直ったかを最初のテスト担当者が確かめるのは確認テストで、テストの活動。
- **d**：誤り。テストの目的と終了基準を決めるのはテスト計画。

## 1.2 なぜテストが必要か？

### 問題3

次のうち、品質保証（QA）の活動として最も適切なものはどれか。

- a. 性能テストで応答時間を測定し、基準を満たしているか確認する
- b. テストで見つかった欠陥を修正し、プロダクトの品質を確保する
- c. 組織全体の品質方針を示し、品質目標を定義する
- d. ふりかえりで見つかった問題をもとに、コーディングルールやレビュー手順を見直す

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：d**

- **a**：誤り。応答時間を測ってプロダクトの品質を確かめるのは品質コントロール（QC）。
- **b**：誤り。欠陥を修正してプロダクトの品質を確保するのは品質コントロール（QC）。
- **c**：誤り。組織の品質方針や品質目標を決めるのは品質マネジメント（QM）。
- **d**：正解。ふりかえりの結果からルールや手順を見直すのは、プロセスに焦点を当てて欠陥の混入を防ぐ品質保証（QA）。


### 問題4

テスト担当者がテストデータの入力を間違えたため、テスト結果を「不合格」と判定し、欠陥レポートを作成した。しかし調べてみると、プログラムに欠陥はなかった。このテスト結果を何と呼ぶか。

- a. 偽陽性結果
- b. 偽陰性結果
- c. 故障
- d. 根本原因

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：a**

- **a**：正解。欠陥がないのに不合格と判定してしまう誤検出が偽陽性。
- **b**：誤り。偽陰性は逆で、欠陥があるのに合格と判定してしまう検出漏れ。
- **c**：誤り。故障は、欠陥のあるコードが実行されて期待どおりに動かない現象。今回はプログラムに欠陥がない。
- **d**：誤り。根本原因は、エラーが起きる根底の理由（知識不足など）。


### 問題5

テストが開発の成功に貢献する例として、最も適切なものはどれか。

- a. テスト担当者が開発担当者と関わらず、独自にテストを進める
- b. テストを行えば、ユーザーの意見を一切聞かなくてもよくなる
- c. SDLCの各段階でテスト結果を使い、次のステージに進めてよいかを判断する
- d. テストはリリース直前に1回だけまとめて行う

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：c**

- **a**：誤り。開発担当者と連携しないと、要件の誤解に気づくのが遅れて非効率になる。
- **b**：誤り。テスト担当者はユーザーの代わりの視点を持つが、ユーザーの意見が不要になるわけではない。
- **c**：正解。SDLCの各段階のテスト結果は、次のステージに進めてよいかの判断やリリース判定に使える。
- **d**：誤り。リリース直前に1回だけでは、欠陥の発見が遅れてコストが増える（早期テストの原則に反する）。


### 問題6

リリース直前に、顧客が本当に求めていた便利な機能を追加した。品質への影響として、最も適切なものはどれか。

- a. 魅力的品質は上がるが、それまでのテスト結果の信頼性が下がり、当たり前品質は下がるかもしれない
- b. 当たり前品質も魅力的品質も、必ず上がる
- c. 当たり前品質は上がるが、魅力的品質は下がる
- d. 機能を追加しただけなので、品質には影響しない

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：a**

- **a**：正解。直前の機能追加で魅力的品質は上がるが、それまでのテスト結果の信頼性が下がり、当たり前品質は下がるかもしれない。2つはトレードオフになることがある。
- **b**：誤り。両方が必ず上がるとは限らない。直前の変更はテスト結果の信頼性を下げる。
- **c**：誤り。上がるのは魅力的品質で、下がるかもしれないのが当たり前品質。逆になっている。
- **d**：誤り。機能追加は、テスト済みの部分にも影響する可能性があるので、品質に影響する。


### 問題7

「開発担当者が要件を誤解した」は、次のどれにあたるか。

- a. 故障
- b. エラー
- c. 欠陥
- d. 偽陽性

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：b**

### 問題8

欠陥と故障の関係について、正しいものはどれか。

- a. 欠陥があれば、必ず故障が起きる
- b. 故障は、欠陥が原因のときにしか起きない
- c. 故障は、テストを実行したときにしか起きない
- d. 欠陥のあるコードが実行されなければ故障にはならず、故障は環境条件で起きることもある

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：d**

- **a**：誤り。欠陥があっても、そのコードが実行されなければ故障は起きない。

- **c**：誤り。故障は本番稼働中にも起きる。テスト実行時だけではない。
- **d**：正解。欠陥のあるコードが実行されなければ故障にはならず、故障は環境条件でも起きることがある。

## 1.3 テストの原則

### 問題9

2つの数の和を求めるプログラムで、3桁までのすべての入力の組み合わせをテストしたところ、故障は1件も見つからなかった。この結果の解釈として最も適切なものはどれか。

- a. 故障が見つからなかっただけで、欠陥がないとは言えない
- b. すべての組み合わせをテストしたので、欠陥がないことが証明された
- c. 3桁までに欠陥がないので、4桁以上の入力にも欠陥はない
- d. 故障が見つからなかったので、妥当性確認も完了した

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：a**

- **a**：正解。故障が出なかったのは「たまたま」かもしれない。テストは欠陥があることは示せるが、ないことは示せない（原則1）。
- **b**：誤り。3桁までしかテストしておらず、4桁以上に欠陥があるかもしれない。欠陥がないことの証明にはならない。
- **c**：誤り。3桁までに故障がなくても、4桁以上でハングアップするような欠陥が残っている可能性がある。
- **d**：誤り。妥当性確認は仕様そのものが正しいかを確かめること。故障が出なかったことで完了するものではない。


### 問題10

入力パターンが膨大で、すべてをテストする時間がない。このときの対応として最も適切なものはどれか。

- a. すべての入力パターンを自動化して、1つ残らずテストする
- b. すべてはテストできないので、テストを行わずにリリースする
- c. ソフトウェアの性質・目的・使われ方から重点的にテストする箇所を絞り、優先順位を付ける
- d. 正しい結果を確認するパターンだけをテストし、エラーになる入力はテストしない

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：c**

- **a**：誤り。全数テストは時間的に不可能（原則2）。自動化しても膨大なパターンは終わらない。
- **b**：誤り。すべてをテストできなくても、重点を絞ってテストすべき。テストせずにリリースするのは危険。
- **c**：正解。全数テストは不可能なので、性質・目的・使われ方から重点箇所を絞り、優先順位を付ける。
- **d**：誤り。故障の多くは、−1や文字などの予期せぬ入力で起きる。エラーになる入力のテストはとても重要。


### 問題11

次のうち、「早期テストで時間とコストを節約」の原則に沿った活動として最も適切なものはどれか。

- a. リリース直前に、すべてのテストをまとめて実行する
- b. 要件定義書のドラフトができた段階でレビューし、曖昧な記述を直す
- c. 本番環境で故障が起きてから、原因を分析する
- d. コーディングが終わってから、設計書を作成する

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：b**

- **a**：誤り。リリース直前にまとめてテストすると、欠陥の発見が遅れて修正コストが大きくなる。
- **b**：正解。要件のドラフトをレビューして早く直すのは、早期テスト（シフトレフト）。静的テストも早期テストに含まれる。
- **c**：誤り。本番で故障が起きてからでは遅く、修正コストが最も大きい。
- **d**：誤り。設計書をコーディングの後に作るのは、早期に欠陥を見つける考え方と逆。


### 問題12

過去のプロジェクトの欠陥分析で、欠陥の8割が特定の2つのモジュールに集中していたことが分かった。次のテストの進め方として最も適切なものはどれか。

- a. すべてのモジュールに、同じだけのテスト工数をかける
- b. 欠陥が多かったモジュールはすでに修正済みなので、テストを減らす
- c. 欠陥が少なかったモジュールを重点的にテストする
- d. 欠陥分析の結果をもとに、欠陥が集中しやすい箇所を重点的にテストする

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：d**

- **a**：誤り。欠陥は一部に集中するので、均等に工数をかけるのは効率が悪い。
- **b**：誤り。欠陥が多かった箇所は、修正後も欠陥が集中しやすい傾向がある。テストを減らすのは逆効果。
- **c**：誤り。欠陥が集中している箇所と逆のモジュールを重点にしている。
- **d**：正解。欠陥の偏在（原則4、パレートの法則）。過去の欠陥分析で集中箇所を予測し、重点的にテストする。


### 問題13

同じテストケースを何度も実行しているが、最近は新しい欠陥がまったく見つからなくなった。対応として最も適切なものはどれか。

- a. テストデータや操作手順を変えるなど、新しい視点のテストケースを追加する
- b. 欠陥はすべて取り除かれたと判断し、テストを終了する
- c. 同じテストケースの実行回数をさらに増やす
- d. 新しい欠陥が見つからないので、リグレッションテストもすべてやめる

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：a**

- **a**：正解。テストの弱化（原則5）。新しい欠陥が出なくても欠陥ゼロとは限らないので、データや手順を変えた新しい視点のテストを加える。
- **b**：誤り。テストが弱化しただけで、欠陥がすべて取り除かれたとは限らない。
- **c**：誤り。同じテストを何回繰り返しても、新しい欠陥を見つける効果は上がらない。
- **d**：誤り。リグレッションテストは、同じテストを繰り返すことに価値があるので続けるべき。


### 問題14

24時間止まらずに動き続けなければならないシステムのテストで、特に重点を置くべきものはどれか。

- a. 画面のデザインが見やすいか
- b. マニュアルどおりにインストールできるか
- c. 他社製品より機能が多いか
- d. 過負荷・多重入力・競合・割り込みが起きてもシステムがダウンしないか

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：d**

- **a**：誤り。画面の見やすさは汎用ソフトなどで重視される点で、24時間稼働システムで特に重点を置くものではない。
- **b**：誤り。マニュアルどおりのインストールは、パソコン向けの汎用ソフトウェアで重視される。
- **c**：誤り。機能の多さはテストの重点ではない。
- **d**：正解。テストはコンテキスト次第（原則6）。24時間稼働のシステムは、どうすればダウンするかに重点を置いてテストする。


### 問題15

「入力欄に4桁までしか入らない」という欠陥を直すためにデータベースを書き換えた。その結果、何桁でも入力できるようになったが、処理時間が10倍になり、顧客から「遅くて使えない」とクレームが来た。これを表す原則はどれか。

- a. 欠陥の偏在
- b. テストの弱化
- c. 「欠陥ゼロ」の落とし穴
- d. 全数テストは不可能

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：c**

- **a**：誤り。欠陥の偏在は、欠陥が一部のモジュールに集中すること。
- **b**：誤り。テストの弱化は、同じテストを繰り返すと新しい欠陥が見つからなくなること。

## 1.4.1 テスト活動とタスク

### 問題16

テストベースを分析してテスト条件を明らかにし、「何をテストするか」を決め、カバレッジ基準を設ける活動はどれか。

- a. テスト計画
- b. テスト分析
- c. テスト設計
- d. テスト実装

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：b**

- **a**：誤り。テスト計画は、テストの目的とアプローチを決める活動。
- **b**：正解。テストベースを分析してテスト条件を決め、「何を」テストするかを明らかにするのがテスト分析。
- **c**：誤り。テスト設計は「どのように」テストするかを考え、テストケースを作る活動。
- **d**：誤り。テスト実装は、テストプロシジャーやテストデータを作り、実行の準備をする活動。


### 問題17

テスト実行中、あるテストケースが不合格になった。後続のテストケースの中に、その不合格になった手順を含んでいるため、実行しても不合格になることが分かっているものがある。このテストケースの結果は何として記録するのが適切か。

- a. 合格
- b. 不合格
- c. ブロック
- d. 偽陰性

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：c**

- **a**：誤り。まだ実行しておらず、期待結果と一致したわけではないので合格ではない。
- **b**：誤り。実際に実行して期待結果と一致しなかったわけではない。
- **c**：正解。結果が分かっていて実行する意味がない、または外部要因で実行できない状態はブロック。
- **d**：誤り。偽陰性は、欠陥があるのに合格と判定してしまう検出漏れ。


### 問題18

テスト計画の策定で、最初に明らかにしなければならないものはどれか。

- a. テスト環境
- b. テストケース
- c. テストデータ
- d. テスト目的

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：d**

- **a**：誤り。テスト環境はテスト設計で設計し、テスト実装で構築する。計画で最初に決めるものではない。
- **b**：誤り。テストケースはテスト設計で作る。
- **c**：誤り。テストデータはテスト設計で要件を決め、テスト実装で作る。
- **d**：正解。テスト計画では、まずテスト目的を明らかにする。目的は納期などのコンテキストやテストレベルで変わる。


### 問題19

テストのモニタリングを行わない場合に起きる問題として、最も適切なものはどれか。

- a. テスト活動がテスト目的に沿って進んでいるかを、客観的に判断できない
- b. テストベースからテスト条件を識別できない
- c. テスト環境を構築できない
- d. 見つかった欠陥を修正できない

&nbsp;

&nbsp;

&nbsp;

&nbsp;

&nbsp;

**答え：a**

- **a**：正解。モニタリングがないと、テストが目的どおりに進んでいるか客観的に分からず、終了基準の判断もできない。
- **b**：誤り。テスト条件の識別はテスト分析の活動で、モニタリングがなくてもできる。
- **c**：誤り。テスト環境の構築はテスト実装の活動。
- **d**：誤り。欠陥の修正はデバッグで、開発の活動。


### 問題20

テスト設計の活動として、最も適切なものはどれか。

- a. テストベースを集め、テスト可能なフィーチャーとテスト条件を識別する
- b. テスト条件からカバレッジアイテムを識別し、テストデータやテスト環境を設計する
- c. テストケースを実行する順番に並べ、テストプロシジャーを作る

&nbsp;

&nbsp;

&nbsp;

&nbsp;
