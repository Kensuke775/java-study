## 使うかもしれないテストツール

| ツールの種類 | 何をする | ツールの例 | 個人開発での使い道 |
| --- | --- | --- | --- |
| テスト実行ツール | テストを自動で動かす | **JUnit**（Java）、Selenium・Playwright（画面の自動テスト） | まずは JUnit でコンポーネントテスト |
| カバレッジ測定ツール | コードのどこを通ったか測る | **JaCoCo**（Java） | 通っていない行・分かれ道を色で確認して、テストを足す |
| 静的解析ツール | コードを動かさずに読んで、問題を見つける | （未定。Java 用のものを調べる） | 動的テストの前に回す |
| 性能テストツール | 負荷・スループットを測る | JMeter、k6 | 下の「性能テスト」メモを参照 |
| マネジメントツール | 進捗・テストケース・人の割り当てを管理する | **Jira**、**Backlog**、Redmine、TestRail（テストケース管理） | 個人なら GitHub Issues でも代わりになる |
| 欠陥管理ツール | 欠陥レポートを登録・追跡する | Jira、Backlog、Redmine（マネジメントツールと兼ねることが多い） | 欠陥は Issue に「何をしたら・どうなるはずが・どうなったか・環境・重大度」で書く |
| CI ツール | プッシュのたびに自動テスト | GitHub Actions | 4. 自動化 を参照 |

- ツールを入れるときは、**作る時間・直し続ける時間・お金**（リソース）がかかることを忘れない
- ツールの効果を**期待しすぎない**、**頼りすぎない**

## 基本の考え方

- **シフトレフト**：テストを後回しにせず、できるだけ**早い段階（左）**でやる
- **作る作業ごとに、対応するテストの作業をペアにする**（V字モデルの考え方）
  - テストの**準備**は上から（要件 → 設計 → コード）
  - テストの**実行**は下から（コンポーネント → 統合 → システム → 受け入れ）

| 作る作業 | ペアにするテストの作業 |
| --- | --- |
| 要件定義 | 受け入れ基準を書く／要件をテストの目でレビューする |
| 設計 | システムテストの観点を書き出す／設計をレビューする |
| 詳細設計 | 部品どうしのつながり（統合テスト）の観点を書く |
| コーディング | コンポーネントテスト（JUnit）／静的解析 |

## 1. 要件定義の段階

- [ ] ユーザーストーリーを書く
  - 形：「［役割］として［ゴール］したい。それは［価値］のためだ」
- [ ] 各ストーリーに**受け入れ基準**を付ける（ATDD）
  - 流れで書くなら **Given / When / Then**（シナリオ指向）
  - 条件の組み合わせが多いなら**表**（ルール指向）
- [ ] 受け入れ基準をもとに、**受け入れテストのケースを先に作る**
  - 順番：ポジティブ → ネガティブ → 非機能
- [ ] 要件を自分でレビューする（曖昧な言葉・抜け・矛盾がないか）
- [ ] **リスク**を洗い出して、テストの優先順位を決める（リスクベース）
  - リスクレベル ＝ 起きる可能性 × 影響の大きさ

## 2. 設計の段階

- [ ] 設計を見ながら、テスト観点（何を確かめるか）を書き出す
- [ ] 使うテスト技法を決める
  - 入力の範囲がある → **同値分割法・境界値分析**
  - 条件の組み合わせ → **デシジョンテーブル**
  - 状態が変わる（ログイン中／ロック中など） → **状態遷移**
- [ ] 非機能（速さ・セキュリティ・使いやすさ）で気をつけることを書く

**機能テストの考え方（メモ）**

- ボタンを1個ずつ全部押すのが目的ではない。「**仕様に書いた機能が、そのとおりに動くか**」を確かめる
- 1つのボタンでも、**いろいろな状況**で試す（普通の動き／ダメなとき／境目）
  - 例：購入ボタン → 商品ありで押す・カートが空で押す・在庫が残り1個／0個で押す
- 全部の組み合わせは無理（全数テストは不可能）なので、**しぼる**
  - 技法（同値分割・境界値分析など）で、試す値を選ぶ
  - **リスクの大きい所**（ログイン・決済など）を重点的に、小さい所は軽めに
- 見る数字は「ボタンを何%押したか」ではなく、「**要件を何%確かめたか**」（機能カバレッジ）

**性能テスト（スループット・負荷）のメモ**

- **スループット**＝一定の時間に、どれだけたくさん処理や通信ができるか（例：1秒間に何件の注文をさばけるか）
- **負荷テスト**＝たくさんの人が同時に使っても、遅くならないか・止まらないか
- どちらも**動かして測る**もの（動的テスト）。非機能テストなので、四象限では **Q4**
- 手動ではできないので、**テストツール**を使う（例：JMeter、k6 など。どれを使うかは未定）
- 先に**目標の数字**を決めておく（例：同時に50人が使っても、画面が2秒以内に出る）
- シフトレフト：最後にまとめてやらず、**早めに**小さく測り始める
- AWS（本番に近い環境）と Docker（同じ環境を何度でも作れる）で測る

## 3. コーディングの段階

- [ ] **TDD**：テストを先に書く → 通るように書く → きれいにする（レッド → グリーン → リファクタリング）
- [ ] **JUnit** でコンポーネントテストを書く
- [ ] **統合の前に**、部品ごとにテストする
- [ ] **静的解析**を、動的テストの前に回す（ツールは未定）
- [ ] カバレッジを測る（目安：ブランチカバレッジ）

## 4. 自動化（CI）

- [ ] GitHub Actions などで、**プッシュのたびに自動テストを回す**
  - 中身は主に**リグレッションテスト**（変更でほかが壊れていないか）
  - 効果：すぐ結果が返る（迅速なフィードバック）
- [ ] 自動化には、作る時間と**直し続ける時間**がかかることを忘れない

## 5. 実行と記録

- [ ] 進み具合を数字で見る（実行したケース数、合格・不合格、欠陥の数）
- [ ] 欠陥を見つけたら記録する（何をしたら・どうなるはずが・どうなったか・環境）
- [ ] 欠陥が直ったら**確認テスト**、ほかに影響がないか**リグレッションテスト**
- [ ] 探索的テストもやる（チャーターで目的と時間を決めてから）

## 6. 構成管理

- [ ] コード・テストコード・テストデータを **Git で一緒に**管理する
- [ ] リリースごとにタグを付ける（＝ベースライン）

## 7. 終わり方

- [ ] 終了基準を先に決めておく（例：受け入れテスト全部合格、重大な欠陥ゼロ）
- [ ] 終わったら振り返る（何がうまくいったか、次はどうするか）
